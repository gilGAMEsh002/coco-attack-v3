# 03 提示素材与输出清洗

文档职责：实施计划与检查点；当前进度只查[阶段概述](./阶段概述.md#current-status)，过程证据见[验收记录](./验收记录.md#task-03)，人工结论见[阶段验收](./阶段验收.md#human-review)。本文件不单独维护实施或验收状态。

依据：[主实施方案](../CoCo-Attack%20DSPy%20重建实施方案.md)工作包 B 及 H 的素材准备、[阶段概述](./阶段概述.md)；对应任务书 F2、F4、F7、E4、E5。前置任务：[02 数据契约与实验划分](./02-数据契约与实验划分.plan.md)。


适用裁定：[D06](./验收记录.md#d06)。以下“已有代码/待核查事项”保留编写时背景；已被裁定覆盖的条款按所引决定执行，不重复请求同一确认。检查点统一映射到[阶段验收标准 AC-01–AC-05](./阶段概述.md#acceptance-criteria)，此处不另建验收标准副本。

## 1. 目标与范围

完成两个可独立调用、共用版本和来源记录的能力：

1. 读取既有提示素材，生成有明确组合归属、任务集合和版本的实验三件套；首先支持旧 4 组合的三种 clean 形态。
2. 将模型原始响应转换为后续静态判定与功能测试使用的代码，同时保存提取方式、入口补全、原始内容与失败原因。

本任务不调用模型、不执行代码、不接入 oracle 判定、不实现指标或评估缓存，不重新抽示例或划分数据。新 5 组合可使用通用清洗能力，但没有 clean 素材时不得自动生成其 clean 实验。具体投毒方法和迭代算法不在本任务中设计。

## 2. 当前实现与资产依据

### 2.1 复用已有代码

当前工程已具有以下能力，实施时直接衔接，不按旧 plan 再造一套：

| 已有模块/接口 | 本任务使用方式 |
|---|---|
| `data.contracts` 的 `TaskRecord`、`LoadedTasks`、`CombinationSpec`、`DatasetSelection`、`SplitManifest` | 复用任务、素材路由、示例顺序和划分契约；文本通过 TaskRecord 的有效字段访问，原值及来源继续保留 |
| `data.prepare.prepare_data` | 使用其完成 manifest、任务快照、selection 和 split，不重新运行抽样或修改划分 |
| `assets.artifacts` 的 hash、原子写入及 `assert_fresh_dir` | 生成稳定指纹，拒绝覆盖非空目录，完整写入后发布完成标识 |
| `assets.paths`、`assets.issues` | 复用路径边界、错误记录和退出码约定 |
| `cli.py` 的 argparse 入口 | 增加子命令，不新增第二个 CLI 框架 |

`TaskRecord` 当前区分 `raw`、`effective`、`metadata_provenance`；快照额外带 `_provenance`，不是原始 17 字段文件。读取准备产物时须补专用读取接口，不能把快照直接交给严格原始数据加载器。

### 2.2 素材事实与差异

- 旧 4 组合的素材路径由 `CombinationSpec.clean_assets` 提供，不使用旧 meta 的失效绝对/相对路径作为运行路径。
- `fewshot.json` 已包含四例的任务描述、cot、code 和攻击标记；模板是含实际代码的完整 Markdown，不是可直接调用 `str.format` 的格式串。代码中的字典、f-string 和正则花括号必须原样保留。
- clean few-shot 的开头与末尾都要求生成 cot 和 code。无 CoT 形态必须同步修改开头、示例 cot、末尾要求和输出槽位，不能只清空 JSON 的 cot 字段。
- 当前对旧 4 组合 109 个 0-shot 提示与标准 `instruct_prompt` 的只读比较发现 2 个差异，均为 `BigCodeBench/215`：cwe295、cwe502 的旧提示为 `Thif function`，标准文本为 `This function`。这不是已批准的修正；保持旧素材并在差异报告中列出，不能自动替换或按任务 ID 写死特殊处理。
- 清洗规则来源为任务书 F4 及同目录知识文档；原项目 `src/cocota/evaluation/code.py`、`evaluation/passk.py` 可作行为参照，不成为新应用的运行依赖。参考源码路径及 hash 写入实现说明，不假定旧项目始终可访问。

## 3. 模块边界与公共记录

在 `src/coco_attack/` 下新增 `prompts/` 与 `evaluation/cleaning.py`；允许扩展 `data/snapshot.py` 的读取能力和原 CLI。所有逻辑只依赖标准库，不初始化 DSPy、缓存或凭证。

| 新增记录/接口 | 最小职责 |
|---|---|
| `ExperimentSpec` | 显式组合/oracle 身份、提示形态、实际示例 ID、共同排除 ID、评测 ID、数据/划分引用、提示/物化版本与攻击配置 |
| `PromptExperiment` | 校验后的 meta、fewshot 列表、按 task_id 索引的完整提示文本和来源信息 |
| `CleanResult` | 原始响应与 hash、生成状态、提取代码、最终评估代码及 hash、提取路径、补全动作、语法/入口状态、清洗版本与诊断 |
| `load_prepared_data(data_dir, combination_id)` | 校验完成 manifest、文件 hash、数据契约版本、任务/selection/split 一致性，读取本组合准备产物 |
| `materialize_clean(spec, prepared, assets_root, form, output_dir)` | 生成指定 clean 形态的三件套及来源/差异记录 |
| `load_experiment(experiment_dir, prepared, expected_oracle_id)` | 统一验证新实验三件套，拒绝归属、字段、任务集合或内容 hash 不一致 |
| `clean_output(raw_text, task, generation_status)` | 无副作用地提取代码、按前缀补全入口并返回 CleanResult；不返回 oracle verdict |

实际函数参数可使用上表中的现有记录组合；不得为提示层重新定义任务集合或重复序列化规则。提示物化与输出清洗分别版本化，清洗改动影响后续评估指纹，不应无故使已完成的模型请求缓存失效。

## 4. 实验三件套与 clean 素材处理

### 4.1 输入校验与共同规则

1. 先核对准备产物 `manifest.json` 的 `completion="complete"`、组合/oracle 映射及各文件 hash；不接受缺失或失败的准备产物。
2. 读取当前路由和素材，核对示例 ID/顺序、评测集合与 selection 一致。原素材和已准备任务之间的文本差异单独报告，不能用集合一致代替内容核对。
3. 实验必须包含 `meta.json`、`fewshot.json`、`test_prompts/`，0-shot 的 fewshot 是空列表，但仍保留相同的四题排除集合。不得因 0-shot 无示例而扩大评测集。
4. meta 显式记录 `combination_id`、`oracle_id`、form、实际示例/排除/评测 ID、数据与划分指纹、协议和物化版本、来源文件 hash、攻击配置；不从目录名补猜归属。
5. test_prompts 文件名沿用已验证的 BigCodeBench ID 编码，每个预期任务恰好一个文件；缺失、重复、额外文件或示例泄漏均拒绝发布。
6. 模型可见提示仅来自明确的任务描述和示例素材，不追加当前评测题的 canonical_solution、test、reference_side 或 oracle 判定。审计元数据保留在 meta/manifest，不为了区分缓存混入提示正文。

### 4.2 三种形态

| form | 实现方式 | 必须保持的内容 |
|---|---|---|
| `clean_0shot` | 复制既有 0-shot 的任务提示原始 UTF-8 字节；生成新的显式 meta，fewshot 为空 | 全文与旧 0-shot 提示逐字节一致；数据文本差异另行报告 |
| `clean_fewshot_cot` | 复用既有完整 few-shot 提示和四例素材；不重新生成推理或代码 | 示例顺序、描述、cot、code、开头/末尾及测试题文本保持一致 |
| `clean_fewshot_no_cot` | 从同一带 CoT 素材结构化派生，仅修改明确的 CoT 相关区域 | 四例任务描述与代码、测试题描述、非 CoT 指令保持不变 |

无 CoT 形态的允许变更固定为：删除每例 `### cot` 及其推理区域；派生 fewshot 中保留 cot 键但值为空；将开头和 tail 中的“generate the cot and code”/“generate cot and code”改为对应的“generate the code”/“generate code”；删除 tail 的 `### cot` 槽位；meta 更新 form 与 has_cot。示例 `### code` 和代码围栏保留。

按 Markdown 结构定位 Example/Test、cot/code 区域，识别围栏内部文本，避免把代码字符串或注释中的同名文字当成结构。仅对已确认的指令位置做精确替换，不全局替换 `cot`，不对模板调用 `str.format`。标记不完整、多个可能的边界或指令版本不识别时报告错误，不猜测。

每个派生提示输出允许区间与实际差异；出现区间以外的变化即停止该物化结果发布并整体报告。原始素材始终只读。

### 4.3 攻击配置与触发器边界

clean 的攻击配置显式关闭，trigger 为 null、poison_parts 为空、示例标记为未投毒。clean 路径不调用触发器剥除或注入函数；发现原素材已有触发标记时报告，不静默修改文本。检查独立触发词，不把其他单词内部的 `cf` 字符子串一律当成触发器。

为 F2 保留确定性的触发文本处理函数和显式攻击配置契约：调用方明确启用时才处理文本，先剥除已有独立触发词，再插入第一个字面句点之前，无句点则追加末尾；示例 1 不注入，示例 2–4 与测试题按契约注入。具体字节规则以任务书和知识文档为准，记录版本与处理前后文本；不得把旧新脚本不同的句点规则混用。该函数只处理调用方提供的文本，不生成投毒代码或 CoT，不自动启动投毒实验。

### 4.4 数据集划分与产物发布

本任务在可信准备环境物化固定评测集合，保留原 split 引用，不重新划分。完整素材准备不等于授权方法读取 holdout；阶段 02 的协调器负责按阶段提供数据和物理隔离，不能将这里的全量目录直接挂给方法进程。

旧 4 组合三种形态共 12 个逻辑实验，分别写入 `<组合>/<form>/`。额外保存来源清单、提示 hash 清单和差异报告；所有请求的实验完成验证后才发布批次完成 manifest，失败只保存诊断而不标记可用。

## 5. 输出清洗规则

### 5.1 输入与提取顺序

输入为一个最终生成样本的原始文本、明确的生成状态和 TaskRecord。原始文本完整保存；清洗操作记录处理方式，不回写原始记录。

生成状态非 success 时保留失败原因，提取和评估代码均为空；不能把错误消息或失败响应残片修成成功代码。下游按 F3 将这种失败计作静态 parse_error 并保留分母。状态缺失是输入契约错误，不能默认成功。

成功响应按任务书顺序提取：Python 代码围栏 → 其他代码围栏 → `### code` 段落 → 全文。每一级使用原文顺序的第一个完整候选，不按能否通过测试、oracle 结果或能否解析来挑选“最好”的代码块；不拼接多个候选。围栏/段落提取移除包裹并保留正文缩进；抽取结果统一按后续 D06 的 cleaner-v3 归一 CRLF/CR→LF 并 rstrip 边界尾部空白，不逐行裁剪、不折叠空白行。该裁定替代早期“全文分支按既有语义”的模糊口径，内部文本不因追历史格式而改写。

多代码块、未闭合围栏或额外解释无法可靠处理时保存诊断，不增加基于 LLM 的修复。旧参考实现的第二优先级主要匹配无语言标签的围栏；对其他标签等新增覆盖带来的历史差异须单独报告，不默认为已经对拍一致。

### 5.2 入口识别与函数体补全

- 入口名称来自 TaskRecord.entry_point，前缀来自该任务的 code_prompt；同时核对实际任务描述 `starting with` 中的前缀。两者入口或结构冲突时报告任务来源问题，不猜函数名、不改标准记录。
- 候选已经定义正确入口时保留其代码，不覆盖签名、导入、默认参数或函数体；不能因内部语法错误再套一层同名函数。
- 仅对确实缺少入口定义的裸函数体按任务书进行缩进修正，再拼接原任务前缀。保留提取前、提取后和补全后的代码及各自 hash；没有有效前缀、空输出或无法确认是裸函数体时不凭空补 `pass` 或参考答案。
- 若输出是含其他函数的完整模块却缺任务入口，保留模块并记录入口缺失，不将整个模块强行嵌入 task_func。入口存在性与语法状态分开记录，不把所有缺入口的合法 Python 都当成 AST parse_error。
- 缩进修正不删除注释、危险调用或改变语句顺序；多行字符串等无法在不改变字面量内容的前提下重缩进的情形保留诊断，不能静默改变代码含义。
- 使用静态语法解析检查并记录行号/异常，不 import、exec 或运行候选代码。解析成功不代表可调用或功能正确，实际可调用性由阶段 02 的 Docker 验收覆盖。

### 5.3 下游口径

CleanResult 至少区分生成失败、空输出、提取路径、是否补全、语法状态、入口状态与处理诊断。本任务不生成 target_present/target_absent 等 oracle 结论。

新流水线的静态判定和功能测试使用记录中的同一份最终评估代码；参考历史时同时保留旧提取代码、历史 evaluation_code（若有）和新补全代码的差异。旧系统可能在功能测试时才补入口，不能为追求历史 ASR 一致而私自切换送入 oracle 的版本；此类差异由任务 05 整体汇报并由用户裁定。

`cleaner_version` 随提取、补全或代码归一化规则改变而更新，进入后续评估记录与功能测试缓存指纹。当前不实现任何清洗结果缓存。

## 6. CLI 与产物

扩展既有 CLI，命令为拟实现接口，本次仅编写计划：

```text
coco-attack materialize-prompts --repo-dir <仓库> --assets-dir <只读资产> --data-dir <prepare-data输出> --combination <完整组合ID> --oracle-id <明确oracleID> --form <形态或all> --output-dir <新目录>
coco-attack clean-generations --data-dir <prepare-data输出> --input-jsonl <最终生成记录> --combination <完整组合ID> --oracle-id <明确oracleID> --output-dir <新目录>
```

- 物化命令一次处理一个显式组合，all 只表示本组合三种 clean 形态；`clean_assets=null` 时明确报告未覆盖，不构造替代模板。
- clean-generations 首版支持现有历史 generations 行的 `task_id/repeat_id/status/generation` 字段；外部显式组合与行内 cwe（若有）按既有旧别名映射核对。只有最终样本记录可输入，不能把含多次尝试的原始 ledger 当成多个 repeat。
- 清洗每行都产出对应记录，包括生成失败；同组合/task/repeat 重复或任务未知时报输入错误，不静默覆盖。格式错误与样本代码无法解析分别报告。
- 输出目录必须新建或为空，并与输入目录隔离；三件套和清洗产物用现有原子写入 helpers，不覆盖原资产、prepare-data 结果或历史 run。

物化输出包括三件套、`manifest.json`、`prompt_diffs.json` 与 `REPORT.md`；清洗输出包括逐样本 `cleaned_generations.jsonl`、清洗版本/输入指纹 manifest 与 `REPORT.md`。观察时间不进入稳定语义 hash，不将运行状态和源错误信息伪装成模型提示的一部分。

## 7. 实施步骤与衔接

1. 补齐 prepare-data 产物读取与完整性校验，复用已存在的任务、来源和划分类型；确认 raw/effective 的区别不会被丢失。
2. 实现实验记录和三件套统一校验，先贯通 cwe078 的两种原有 clean 提示，再接入其余旧组合。
3. 实现无 CoT 的结构化派生与差异报告，完成三种形态的提示 hash 和元数据；不为现有文字差异添加任务 ID 特例。
4. 独立实现确定性触发文本契约，确保 clean 路径完全不调用；不展开投毒方法设计。
5. 实现输出提取、前缀核对、裸函数体补全和 CleanResult，保留不同处理阶段的代码，接入清洗 CLI。
6. 汇集提示与清洗差异，交给任务 04 接入判定与指标、任务 05 做整体历史对拍；所有待裁定差异保持显式状态。

## 8. 汇入阶段统一验收的检查点

不建立本子任务的独立测试套件或验收记录。使用同一组参数化素材和少量清洗样例，在阶段验收时集中检查。

| 集中检查 | 通过条件 |
|---|---|
| 提示复现与无 CoT 派生 | 旧 4 组合三种形态任务集合一致；0-shot/带 CoT 原提示逐字节复用；无 CoT 只发生允许变更；代码花括号与字符串未被格式化破坏 |
| 实验契约与确定性 | 三件套缺失、归属错配、任务泄漏或素材边界不明被拒绝；同输入/版本重复物化字节一致；clean 不注入；触发函数用少量边界文本验证 |
| 清洗与失败保留 | 推理文字包裹、围栏、段落和裸函数体共用一组样例；完整入口不二次包裹，失败/空输出不变成可用代码，所有样本保留 |
| 版本与差异证据 | 提示变更与清洗变更分开版本化；多候选不按判定挑选；已发现提示文字差异及新旧清洗差异可审查，未裁定不写成通过 |

裸函数体补全后的真实可调用性留到阶段 02 的 Docker 检查。若历史对拍出现差异，先汇报范围、数量、代表样本和影响，由用户决定修正方案；不为消除差异而擅自改变提示、清洗规则或 oracle。

## 9. 完成条件

三种 clean 形态可由统一命令稳定物化，三件套归属与集合校验完整，清洗接口能输出可追溯代码及失败状态，且所有差异与检查点已进入阶段统一审查材料，才可标为本任务实现完成。

阶段验收通过须另有集中检查与人工审查证据；计划存在、CLI 可运行或代码能解析都不能代替通过。本任务不代替任务 04/05 的判定与历史校准，当前实施状态统一维护在阶段概述。
