> 范围：阶段 01（领域基座与历史校准）五个子任务实施期间，主 Agent 与子代理协作、研究代码实施、验证与验收、仓库卫生方面实际踩过的坑与可复用规则。

## 一、协作模式与子代理使用

### 1.1 子代理能力差异极大，任务要按能力分配
- **现象**：`reviewer` 与 `research` 子代理在本次环境中**没有 shell/执行工具**，只能静态阅读源码；`debugger` 有 shell，能真正跑探针。
- **后果**：让 reviewer 去"验证运行时行为"会得到基于推理的结论（有时正确，但无法执行）；research 明确报告"无法运行命令，仅静态重建"。
- **规则**：
  - 需要**实际执行/构造边界/复现**的任务 → `debugger` / `experiment`。
  - 需要**独立代码审读/找风险点**的任务 → `reviewer` / `research`，但不要期待它们给出运行时结论。
  - 在 prompt 里明确写"你可能没有 shell，请说明哪些结论无法执行验证"。

### 1.2 不要把子代理的终止状态当成主 Agent 的状态
- **现象**：reviewer 返回 "I've reached the maximum steps..."，我误以为**主 Agent** 达到步数上限，于是在汇报里写了"我不能再使用工具"，造成误导。
- **规则**：子代理的 `max steps / cancelled` 只是**该子代理**的状态；主 Agent 只有收到明确的系统限制才停止。汇报时严格区分"子代理受限"与"主流程受限"。

### 1.3 给子代理的探针/审查任务要"有界、分优先级"
- **现象**：第一轮 debugger 给了 5 大组、20+ 子项，结果被取消；第二轮拆成"优先 1–3 组，4 组时间允许再做"后顺利跑完，并发现了真实 bug。
- **规则**：每轮子任务只覆盖一个主题；给出编号的、可勾选的检查项；明确"时间不够可跳过哪组"；要求"精简编号结论 + 精确命令 + 观察结果 + 分类（真 bug / 预期 / 测试缺口）"。

### 1.4 静态审查与动态探针是互补的，不要只做一种
- **现象**：静态 reviewer 找到了 oracle 分支内 alias 泄漏、参考校准一致率分子分母不一致、`formal` 标志恒为 False 等**逻辑/契约类**缺陷；但它**没有发现** `_assigned_names` 漏掉 `Subscript`/`Import` 导致 `if False: opts["shell"]=True` 仍泄漏——这是 debugger 动态构造探针才暴露的。
- **规则**：涉及算法/判定逻辑的变更，至少各做一次静态审查 + 动态对抗探针；探针要覆盖"看起来无害但绕过分支隔离"的 AST 形态（下标赋值、import、walrus、try/except、for、kwargs 解包）。

### 1.5 子代理结论必须主 Agent 复核后落地
- **现象**：reviewer 的多数发现被采纳修复；但它对 `llm_judge_rate` 分母的"缺陷"实际符合任务书 F6（"检出数 / 固定样本数，另列失败/缺失"），对参考重组公式的疑虑也因任务书明确要求 `code_prompt + canonical_solution` 而不改。
- **规则**：子代理的"应该怎样"可能与上层需求冲突；逐条对照任务书/计划再决定改或不改，并把"不改的理由"写进验收记录。

## 二、研究代码的实施纪律

### 2.1 区分"实现缺陷"与"实验差异"
- 阶段 01 出现的两类东西不能混：
  - **实现缺陷**（要修）：类型校验只写清单不报错、`_iter_jsonl_lenient` 作用域硬编码、`project_root` 父目录索引差一、`registry_id.lower()` 与 `combination_id` 不匹配、oracle 分支 last-wins、alias 泄漏、`formal` 标志恒 False 等。
  - **实验/历史差异**（只报告、先汇报）：cwe078 31 vs 历史功能参考 30、cwe089 4/5 标签边界、历史清洗字节差异。
- **规则**：不要为了让数字好看去改 oracle/清洗/指标；差异先整体汇报，由用户裁定。

### 2.2 不要反向拟合历史字节
- **现象**：为了让历史对拍"代码逐字节一致"，先尝试"空白行归一为空行"规则；结果它匹配了 gpt-4o cocota 的 3 处，却**破坏了 deepseek 0shot 中原本已匹配的 124 个样本**——证明历史 run 之间用了不同的清洗版本。
- **规则**：为未来实验定义**自己的规范形式**（`cleaner-v3`：CRLF/CR→LF + 边界 rstrip，保留内部字节），不追历史字节。对拍时用 `ast.dump` 等价把差异分成"外观（不阻塞）/阻塞"。

### 2.3 "只读资产"的例外必须显式、版本化
- **现象**：用户裁定"修 oracle 就**直接改** `oracles/cwe078_0.py` 本体，不要在 oracle 外面打补丁"；随后又要求把补丁逻辑并入本体。
- **规则**：
  - 默认资产只读；任何修改都要用户明确授权、记录原因、`bump` 版本（如 `ORACLE_VERSION=2`），并把源码 hash 写进指纹。
  - 用户要求"改本体"时，不要在外部包一层补丁——不利于长期单点维护。
  - 用"链路前后 `asset_manifest.json` 逐字节一致"作为只读证明（授权修改的文件除外）。

### 2.4 修改判定语义要成体系，避免"补丁式"扩展
- **现象**：oracle v2 先只合并 `values`，遗漏了 `callable_aliases/partial_shells/mapping_shells/module_aliases`，也漏了 `node.test`、常量死分支、`Subscript`/`Import`；被两轮复核逐步逼出来。
- **规则**：改动判定逻辑时，先列出**全部会跨分支变化的状态**（值绑定、导入别名、可调用别名、partial、kwargs/下标映射）与**全部绑定 AST 形态**，一次性设计隔离+合并策略，再补回归矩阵。

### 2.5 失败不能变成成功、未定义不能变成 0
- 生成失败/空输出 → `parse_error` 且留在分母；工具/judge 未接入 → `defined=false` + 原因，绝不填 0；`target_absent` ≠ 安全；历史 verdict 缺失 → `null`，不反推。
- **规则**：把这几条当评审清单，任何"补默认值/静默剔除/用 0 兜底"都是缺陷。

## 三、本轮发现的典型缺陷模式（阶段 02–04 的检查清单）

| 模式 | 实例 | 检查方法 |
|---|---|---|
| 校验只记清单不报错 | `type_violations` 写 manifest 但不产生 issue | 每个"统计字段"都要问：它是否触发 error？ |
| 作用域/前缀硬编码后复用 | `_iter_jsonl_lenient` 固定 `reference_eval` 前缀，被 task/legacy 复用时误报 | 复用函数时检查 code/scope 是否由调用方传入 |
| 路径/索引差一 | `project_root()` 用 `parents[2]` 实际应是 `parents[3]`；用 cwd 掩盖 | 从任意 cwd 运行 CLI 的冒烟测试 |
| ID 映射不一致 | `registry_id.lower()` 与 `combination_id` 不匹配导致计数差异漏报 | 断言前先打印两侧键集合 |
| last-wins 覆盖语义 | oracle 分支赋值取最后一个分支 | 构造 if/elif/else、无 else、常量死分支 |
| 分支状态泄漏 | alias/subscript/import 在分支内泄漏 | 逐状态、逐 AST 形态构造对抗探针 |
| 恒假判断 | `sampling == formal_spec` 因多一个 `model` 键永远为 False | 对"标志/布尔"字段断言其在正常输入下能为 True |
| 统计口径小错 | `pass_at_k.sample_count` 求和整个 dict；`None==None` 判为 match | 对边界（双方未定义）单独断言 |
| 读回不校验 | 重复 `task_id`、`from_json` 裸 `KeyError` | 篡改副本测 hash/schema/重复/结构错误 |
| 覆盖式编辑误删 | 编辑时把函数体替换成只剩 `def` 行（测试文件多次发生） | 每次编辑后立即 `compileall` + 跑相关测试 |

## 四、验证与验收纪律

1. **每个代码改动后立即 `python -m compileall` + 跑相关测试**；本次多次因为"改完没复验"而需要回头补。
2. **先窄后宽**：单元/纯函数 → 单组合集成 → 全链路；阶段集中验收用一个端到端入口串起来（`tests/test_stage_acceptance.py`）。
3. **对拍要精确**：布尔、样本键、分子/分母零容差；汇总相同不代表逐样本相同——报告必须同时给"任务级 ASR"和"逐样本不一致数"。
4. **区分报告生成完成与验收通过**：manifest 分别保存 `completion` 与 `acceptance_status`；有差异仍可交付报告，但不能标"一致/通过"。
5. **人工审查材料集中**：证据写进 `验收记录.md`，收尾摘要写 `阶段验收.md`；不要新建互不相关的验收文件。

## 五、上下文与长任务管理

- 长任务（如阶段 01 五个子任务）要**分批推进、每批收口**：实现 → 测试 → 独立复核 → 修复 → 复测 → 记录。
- 不要把整仓库反复交给不同子代理读；给每个子代理**具体问题 + 已知上下文 + 期望输出 + 约束**。
- 子代理会污染上下文，主 Agent 只保留结论与证据；具体探针脚本放 `/tmp`，不进仓库。
- 遇到"用户设定权限需确认"的操作（如 `git push`），在用户明确指令后才执行。

## 六、仓库与数据卫生（上传经验）

1. **绝不要 `git add -A` 之前不设 `.gitignore`**：本次 `third_party/` 里 CodeQL 有 1.1GB、`.opencode/node_modules` 63MB；不先忽略会误传。
2. **许可证是硬约束**：`third_party/codeql/LICENSE.md` 明文禁止 **share/publish/distribute/lend**；不能上传。BigCodeBench 是 Apache-2.0 且是嵌套 git 仓库（会变成 submodule 指针），也一并排除、改用上游安装。
3. **密钥**：`.env` 必须被忽略且不在索引；发现疑似 key 的公开基准样例要提示用户确认/脱敏/轮换。
4. **大文件**：单文件 >100MB 会被 GitHub 拒绝，>50MB 会告警；推送前统计体积与最大文件。
5. **remote 管理**：保留 `upstream`（原始 dspy）与 `origin`（自己的仓库）两个 remote，避免误推到官方仓库。

## 七、可复用的 Agent 工作规则（阶段 02+）

- [ ] 每个子任务：先读 plan/任务书 → 确认契约边界 → 最小实现 → 立即测试 → 记录。
- [ ] 涉及判定/指标/缓存/划分的改动：**静态审查 + 动态探针各一轮**，再复测。
- [ ] 任何差异先分类：实现缺陷 / 实验差异 / 环境阻塞；后两者先汇报，不擅自改。
- [ ] 只报告"实际执行过"的结果；未执行/未验证的明确标注。
- [ ] 版本化一切会影响指纹的东西（提示、清洗、oracle、评估器、缓存键）。
- [ ] 提交前做仓库卫生检查：密钥、体积、许可证、嵌套仓库、`.gitignore`。
