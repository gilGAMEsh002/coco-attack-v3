## 1. 目标与责任边界

将固定的 `final_code` 和任务自带测试交给已验收的 Docker 执行后端，获得可区分通过、不通过、不可用和未完成的单样本功能结果；只对符合 F1 的完整功能测试结果建立持久缓存，恢复时补做缺少有效结果的样本，并用当前固定任务集合重新计算 pass@1/@3/@5。

| 本任务负责 | 其他任务负责 |
| --- | --- |
| 输入与样本归属校验、功能 harness、测试结果分类、裸函数体补全后的真实可调用性 | 阶段 01：数据、cleaner、静态 oracle 和纯指标公式；本任务复用其接口 |
| 接入现有 ExecutionSupervisor、增加受控 functional 镜像入口、校验内层功能结果 | 子任务 01：通用隔离、资源限制、进程回收及信封/文件收集；新增入口沿用这些能力 |
| 分阶段 SQLite 功能缓存、结果完整性、sample 恢复、local_test 记账接线、pass@k 聚合适配 | 子任务 02：生成/DSPy 响应缓存与统一 ledger；阶段隔离按 D06 不要求调用路径强制 |
| 功能评估服务与功能层接线（按 D06 不做越权检查） | 子任务 04：SAST/judge、动态/真实性层；子任务 05：完整评估顺序、报告和真实 API 验证 |

功能执行面向显式配置的任务集合，不按静态命中、`reference_side` 或 clean/target 标签筛选样本。数据入口支持标准 9 组合；动态/真实性层只覆盖旧 4 组合的限制不套用到功能测试。实际运行范围和依赖可用性逐组合列明，本任务不运行全量 clean 基线、不调用模型、不增加生成样本。

## 3. 输入校验、身份与功能记录

### 3.1 固定输入清单

先建立一次功能评估的不可变 `functional_config.json` 与输入清单，显式声明：任务集合及 split、采样配置、逐样本原批次/生成文件/清洗产物、执行 profile、harness/功能判定版本、k 集合、缓存目录、ledger 位置、输出目录。k 本期为 1/3/5；不从已有成功记录推断任务集合。

1. 先做阶段授权，再读取该阶段的样本与缓存。校验组合/oracle、任务成员、示例互斥及 sample 七字段；复算 sample_id 与原始生成哈希，核对生成行、清洗行及任务快照的一一对应。
2. 校验准备/清洗 manifest、各自实际文件哈希和状态；重新计算 `final_code` 字节哈希，不能只相信记录中的 hash。缺关键身份或来源时报告输入错误，不构造占位指纹继续缓存。
3. 按来源登记原始 `run_config.json` 的实际字节哈希及副本，保留原有结构哈希作审计。禁止为了迁移路径或补字段重写旧配置；旧清洗/生成产物保持只读。
4. 每个参与功能测试的任务必须有非空 test、明确 entry_point 和测试来源；对测试源码做静态结构/语法检查。缺测试是启动自检错误，不是生成样本未通过，也不能悄悄删题。
5. 清洗或生成文件追加后，可通过当前有效快照重新绑定其逐样本记录；整文件哈希用于核查该次输入，功能缓存不将其作为每个样本的失效条件。旧样本原配置、prompt、raw/final_code 和测试均未变化时，应保持原缓存键。
6. 跨批次仅接受显式来源清单，每行保留原 sample/batch/配置哈希。task/repeat 相同而身份不同的行不能随意覆盖或拼入同一评估矩阵；由输入映射明确拒绝歧义。追加 repeat 只登记新样本，不改旧样本身份。

### 3.2 功能结果类型

在评估包增加 `FunctionalResult`，至少分开保存：

| 字段组 | 内容 |
| --- | --- |
| 身份 | 完整 sample_id/七字段、原批次和 source、组合/oracle、执行 attempt、功能评估配置引用 |
| 功能结论 | `outcome=passed/failed/unavailable/error/incomplete`、`passed=true/false/null`、reason；严格布尔，不接受字符串或整数冒充 |
| 完成与覆盖 | `tests_discovered/tests_run`、成功/断言失败/errors/skipped/expectedFailure/unexpectedSuccess 计数、`suite_completed`、失败发生阶段及必要测试详情 |
| 执行事实 | 原 ExecutionResult 引用、退出码、超时/OOM/限额、资源和镜像指纹、清理状态；与功能结论并存 |
| 完整性与缓存 | 指纹结构/哈希、功能载荷/必要文件引用及哈希、`cache_eligible`、复用来源；已发布原结果不可被本次 cache_hit 标记改写 |
| 记账 | 原执行 accounting_id、耗时、local_test 执行/费用来源；缓存读取只引用，不重复计执行成本 |

`suite_completed` 表示测试加载和运行按协议结束，包含断言不通过的正常结束；不表示全部成功。`passed` 表示是否已有确定的功能结论；没有完整执行证据时保留 null，不能一律压成 false。程序入口存在、AST 可解析、外层 result_valid 或退出码 0 均不能代替功能判定。

## 4. 功能 harness 与隔离执行

### 4.1 组装和运行语义

新增 `docker/evaluator/functional_runner.py`，作为可信镜像内的固定入口。宿主只物化本样本的 `solution.py`、`tests.py`、必要 fixture 和请求文件，登记精确字节哈希；所有候选导入、测试发现和执行均在容器中进行，包括 mock 生成样本。禁止在主机 import/exec 候选或通过 unittest discovery 导入测试。

组装参考只读 vendored `third_party/bigcodebench/bigcodebench/eval/__init__.py`：以 `final_code + "\n" + task.test` 在同一 `__test__` 模块命名空间中编译并执行一次，再取 `TestCases`，用 `unittest.TestLoader.loadTestsFromTestCase` 和 `TestResult` 运行。保留需要的模块注册和标准上下文，不直接调用 vendored `unsafe_execute/untrusted_check`。

具体要求：

1. 保持 `solution.py` 与 cleaner 的 final_code 完全一致；组装后的测试程序另记 hash 和代码/测试边界。不再次拼 `code_prompt`、不修改缩进、换行或字符串，也不追加一个“修好的”函数。若需要定位语法错误，可分别 compile 检查，但不可为诊断把候选顶层执行两遍。
2. 通过任务给定测试调用入口，不猜函数参数做额外试调用。完成代码/测试加载后核对 entry_point 是所需可调用对象；入口缺失与测试来源缺失分开归因。
3. 固定从任务测试的 `TestCases` 加载，不扫描任意目录，不把生成代码自己新增的测试类纳入通过依据。记录 discovered 数与 loader 错误；零测试不能判通过。
4. 关闭 failfast，保留普通测试及 setup/teardown 错误。尽可能执行所加载的完整 suite，记录失败/errors 与其他状态；不照抄 vendored 只检查 failures/errors、可能把跳过当作通过的宽松逻辑。
5. 候选/测试的输出通过既有有界日志通道收集；runner 保存结构化结果，不能通过解析打印的 `OK` 或候选自行输出的 JSON 判定通过。
6. 内层执行超时与外层总 deadline 明确分配：为入口启动、结果发布和 SIGTERM→SIGKILL 留出有限余量；任何阶段挂死仍由现有容器监督兜底。不移植 vendored 的主机 monkeypatch 或 `reliability_guard` 来替代 D 的隔离。

本地静态核查发现标准 9 组合的 test 均有 `TestCases` 形态，未发现 skip 装饰器、expectedFailure、subTest 或 setUpClass；这是输入形态核查，不证明实际运行不会发生跳过或动态错误。当前协议对意外跳过/expectedFailure 等单列诊断并不认定通过；遇到真实资产需要此类语义时按 C 汇报，不自动增加豁免。unittest 结果分类参考 [Python 3.14 官方文档](https://docs.python.org/3.14/library/unittest.html#unittest.TestResult)。

### 4.2 依赖、入口与结果收集

复用子任务 01 的 profile、安全设置、有界 tmpfs、nonce 信封、归档和回收。增加 `entry_id=functional`，其 child argv 固定指向 functional_runner，不接受方法提供的 shell 命令。镜像只加入可信 runner 和经核实的必要依赖/fixture，不打包全量数据、参考解或模型凭证；执行镜像变化后更新实际 image ID/摘要和锁文件指纹，并补跑适用的 AC-01/依赖检查，再运行生成代码。

运行时不得联网安装依赖或读取宿主服务。依赖清单覆盖情况在相同隔离配置下核验：测试要求的已声明库/系统工具缺失为环境不可用；候选自己引入不存在的库、错误参数或运行异常可作为候选失败。不能只看到 `ImportError` 就统一归因于候选，也不能为了通过而放开网络、改测试或换解释器。需要本地服务时使用隔离容器内受控 loopback，遵循 D。

runner 原子写 `payload.json`，至少包含功能 schema/harness 版本、sample 与输入哈希、加载/执行阶段、测试计数/结果和完成标记。外层 entrypoint 发布带身份和 nonce 的 `result.json`。宿主功能适配器在现有外层校验后继续检查：

- `payload_valid=true`，内层对象结构和严格字段类型正确，输入/代码/测试/harness 指纹与本次请求一致。
- 测试计数、完成标记与结论自洽；正常通过须非零测试、suite 完整结束、所需测试全部成功，无错误/跳过等未覆盖项。
- 必要附件已归档、为受限路径下普通文件且哈希匹配。外层附件收集可能跳过文件，所以不能只看 attachments 列表存在；必要日志/详情缺失时不得发布可复用结果。
- 原始退出/超时与功能结果分别保留。不得用 `ExecutionResult.ok` 或单个 `error_class` 直接决定功能通过或可用性。

完整有效结果在入口后续挂死、退出异常后仍保留；但清理未确认时停止新执行，先回收，不提交新的可复用缓存条目。nonce 和哈希用于身份/完整性校验，不被描述为候选无法干扰同容器内测试的完整证明。

## 5. 功能状态、分母与缓存资格

以下是 B/D/F 在功能层的落实；状态分别进入逐样本报告，不改静态 verdict。

| 情况 | 功能与指标处理 | 是否写功能缓存 |
| --- | --- | --- |
| 已有明确生成失败，或成功但 final_code 为空 | `passed=false`、reason 区分生成失败/空输出，留在该题 n 中；无需启动容器，不假称执行了测试 | 否；属于确定性输入处理，可从生成/清洗记录重建 |
| 候选语法错误、缺入口或候选加载失败，来源可明确归因 | `passed=false`，保存代码/加载阶段诊断，留在 n 中；不把它误报为测试环境 unavailable | 否；suite 未正常完成，不扩大 F1 的缓存范围 |
| suite 正常完成，全部所需测试通过 | `passed=true`、`suite_completed=true`；该样本计入 n 和 c | 是，前提是完整性、环境及清理检查均满足 |
| suite 正常完成，有断言失败或可归因于候选的测试运行错误 | `passed=false`、保留失败详情；计入 n，不计 c | 是；失败不是拒绝缓存的理由 |
| 缺已声明测试依赖/工具、Docker 或镜像不可用 | `passed=null`、unavailable，列出原因；不能补 false 或删题后发布均值 | 否 |
| 测试源码/加载器错误、零测试、harness 异常、结构或身份/附件损坏 | `passed=null`、error；明确是评估输入/执行问题，不当候选失败 | 否 |
| suite 有意外 skipped/expectedFailure 等未验证项 | 保存计数，`passed=null`，说明所需测试未全部验证；unexpectedSuccess 等异常类别同样显式报告 | 否；不把未验证的成功假设落入缓存 |
| 内层有可信、完整的终止原因，明确候选超出规定执行时限 | `passed=false`、candidate_timeout，留在 n；`suite_completed=false` | 否；超时未完成测试，不能复用为正常完成结果 |
| 仅外层超时/OOM/被 kill，无法得到可信功能载荷 | `passed=null`、incomplete，保留限额和中断事实；不从退出码猜功能失败 | 否 |
| 完整有效 suite 结果已经发布，随后 supervisor/进程退出异常 | 保留原 true/false，另记退出/超时异常；不要仅因外层非零退出抹掉结果 | 仅在确认 suite 正常完成、必要产物完整、无影响判定的基础设施错误且清理完成时可写；不以异常类型单独决定 |

若无法区分候选错误和环境故障，保留未知原因等待核查，不自动选有利于指标的一侧。timeout 的“是否得到确定结果”和“是否可缓存”是两个独立问题，不能用 `passed=false` 推导 `cache_eligible=true`。

本任务不要求所有参考解功能测试均通过。参考解仅用于少量有来源的接线检查，不能将 reference_side 或既有静态校准结果当成功能真值；新增差异按[校准与差异 C](../CoCo-Attack%20DSPy%20重建实施方案.md#calibration)整体报告。

## 6. 功能缓存指纹与 SQLite 持久化

### 6.1 指纹规则

构造版本化 `FunctionalFingerprint`，将下列字段规范序列化后 SHA-256；保留结构正文用于解释 miss 原因。输入有记录但哈希失配时拒绝篡改输入；版本或依赖合法变化时用新指纹重算；缺不可恢复的身份/来源时先报配置问题，不用 null/默认值凑齐。

| 指纹内容 | 来源与规则 |
| --- | --- |
| sample_id、stage、原 batch/组合/oracle 归属、generation status | 生成记录和授权后的采样清单；不同采样身份即便代码相同也不跨样本复用 |
| `run_config_bytes_sha256` | 原生成批次配置文件的实际字节哈希，不能使用现有结构 hash 替代；追加批次保留旧引用 |
| 本样本 prompt/raw generation/final_code 哈希 | 从原始内容复算；不使用全量 prompt 集合或整个 generations 文件哈希使其他样本连带失效 |
| 任务快照、test、entry_point 和必要 fixture 哈希 | 固定来源、内容及实际测试组装输入；目录扫描位置和当前时间不作为依赖 |
| cleaner 版本、功能 adapter/harness 版本与源码哈希、结果 schema | cleaner-v3 按阶段 01 D06 继承；语义实现变化有可追溯版本，不只用文件名判断一致 |
| 执行镜像不可变内容标识、依赖锁和执行语义配置 | 使用实际 image ID/已有分发摘要，保留 Python 与平台来源；资源/超时、网络模式、入口和输出限制均有绑定 |

缓存键不包含 execution attempt、nonce、容器名、输出路径、耗时或缓存读取次数；这些是原执行证据，不能让每次恢复生成新键。执行 profile 的现有整对象 hash 可作审计，功能键使用明确的执行语义字段，避免只因临时目录迁移误判样本依赖变化。

oracle_id 是归属字段，但静态 oracle 源码/命中 verdict 不决定功能测试结果，不单独作为功能缓存失效条件。若其他必需字段（例如原 run_config 字节）随上游配置变化，则仍按 F1 失效。阶段 01 D07 的 AST 等价外观分类不能替代字节指纹匹配；除 cleaner 已定义的规范归一外，不为“看起来一样”的代码另建等价缓存。

### 6.2 最小存储结构

使用标准库 sqlite3，实现现有 `EvaluationCache` 协议。建议在显式 cache root 下分别存放 `functional-v1/search/`、`functional-v1/holdout/`，各有 `index.sqlite3` 和持久 `artifacts/`；校验目录及祖先链接解析后确实分离，禁止方法挂载。只实现一个功能缓存，不创建 oracle/SAST/judge/动态/真实性结果索引。

SQLite 保留少量结构：

- `metadata`：schema、固定 stage、缓存根身份；数据库内 stage 与目录/请求不符即拒绝。
- `results`：唯一键 `(sample_id, fingerprint_sha256)`，完整指纹 JSON、FunctionalResult JSON、原执行身份/结果哈希、必要文件清单和记账引用。插入前强制执行 cache_eligible 检查；正常不通过的结果与通过结果同等保存。

首次实现逐样本串行执行、一个可信 writer 即可。复用 run 锁，并对共享同一阶段缓存的写入者使用简单本机排他锁或明确拒绝并行控制；不建设分布式缓存、后台回收服务或复杂淘汰策略。数据库事务只覆盖索引提交，不跨整个容器执行持锁事务。

使用显式事务和非 OFF 的持久化设置，单写入者可采用 rollback journal + `synchronous=FULL`，无需为本期额外建设 WAL 并发方案。SQLite 的提交原子性只覆盖数据库，外部日志/附件需由应用按下面的顺序发布，不能假定一次 SQL commit 同时提交文件。[SQLite 原子提交说明](https://www.sqlite.org/atomiccommit.html)

### 6.3 写入、读取与损坏处理

写入顺序固定为：**隔离执行结束并确认回收 → 校验并归档到持久盘 → 记录实际执行事件 → 发布缓存所需文件 → 提交 SQLite 索引 → 导出本次功能记录**。

1. 缓存必要附件放到缓存拥有的不可变目录，或明确长期保留的归档目录；不能指向会清理的 tmpfs。采用临时文件、fsync、原子替换和必要目录同步后再提交索引，不以“文件名存在”代表完整发布。
2. 索引中保存完整功能结果及各必要文件的相对路径、大小和哈希。写入不覆盖同键的不同内容；发现冲突保留两次执行证据并报错，不静默选最后一次。
3. `get` 先核对当前授权、stage 和完整指纹，再验证结果结构、sample/输入身份、原执行结果和必要文件。命中返回原功能结果及 reuse source，不复制成一个新生成样本，也不覆盖原始成本/耗时。
4. 缺文件、半成品或结果损坏视为无有效缓存，记录明确 miss/invalid 原因后隔离重算；旧损坏条目失效并保留诊断。整个数据库损坏时保留原库证据，显式报告缓存不可用后受控重建，不能无声清空并报告正常命中率。
5. SQLite 提交前中断可能留下无索引的完整文件；同一次评估恢复可按持久执行清单重新校验并补索引，不能随意扫描历史目录将未知文件当成缓存。提交后导出前中断，直接读有效索引补导出，无需再次执行。
6. 本次缓存命中标记只写在消费记录/报告中，原缓存结果不可变。缓存读取不追加 local_test 执行费用。缺功能资格的 unavailable/error/incomplete 占位只存审计，不写可复用结果索引。

## 7. sample 恢复、阶段标识与执行记账

### 7.1 每样本运行流程

```text
阶段授权与输入校验
        ↓
确定性生成失败/空输出处理，或计算功能指纹
        ↓
查询本阶段缓存 ──有效命中──→ 记录复用来源
        ↓ miss
核对当前执行隔离前置条件 → 物化单样本 → 新 execution attempt
        ↓
ExecutionSupervisor → 内层功能校验 → 归档/记账 → 合格结果入缓存
        ↓
按完整 sample 身份导出功能记录，重新聚合当前集合
```

合法缓存命中可使用此前完整执行结果，无需为了命中再启动 Docker。若当前 Docker 不可用，miss 样本报告 unavailable，命中来源照常列出；这些复用结果不能冒充当前机器新的 AC-01 证据，也不能覆盖未评测样本导致的指标未定义。

本任务不得按 ASR 命中率挑选是否功能执行。完整管线 G 的“核心结果先落盘”由子任务 05 串接；独立 functional 命令允许验证本层，报告注明不是完整多层评估。

### 7.2 恢复与幂等

恢复以 sample 加当前功能指纹为单位。获得 run/cache 控制权后，先处理本 run 遗留容器，再读取有效缓存和已归档执行清单：

- 有有效缓存：跳过执行，只重建缺失的导出或汇总。
- 已完整执行/归档但未入缓存：校验原请求、内层结果、清理状态及必要文件，补执行记账/索引；不能仅因上次进程没有正常退出就重跑。
- 只有 tmpfs 半成品，或宿主重启导致未归档结果丢失：旧 attempt 按归属收尾，明确缺口，以新 execution attempt 重做同一 sample；不重新调用模型。
- 旧结果不具缓存资格：恢复时不能把 checkpoint 当缓存跳过；可按明确配置重新评估，失败后不无限自动循环。执行重试有上限，断言失败不因“不满意”自动重试。
- 版本不一致但容器归属明确：沿用 D02 清理；结果复用仍严格检查功能指纹，不能把清理例外扩展成缓存例外。

新增 repeat 只执行新增身份，旧结果按各自原指纹保留；汇总不因 cache hit 增加 n。任何不完整输入或执行范围都明确列出，不能删掉未完成任务后发布看似完整的 pass@k。

### 7.3 local_test ledger 接线

复用 `execution_recorded`，payload 增加 `role=local_test`、`accounting_id`、evaluation run/source run、sample、execution attempt、执行配置、耗时和结果来源。accounting_id 由稳定的所属 run/sample/attempt 派生，覆盖成功、失败、超时、重试和随后被淘汰的候选；不使用每次 append 随机生成的 event_id 作执行去重键。

由唯一 writer 在 run 锁内回放并检查 accounting_id 后追加；同 ID 同内容不重复计账，冲突报错。ledger、SQLite 和导出不是一个跨文件事务，以稳定身份和归档事实补齐中断窗口，不引入两阶段提交系统。若沿用 ledger 尾记录恢复，追加前须实际保存并处理尾部半行，不能只写 `.tail` 后继续向损坏尾部拼接新 JSON。

独立功能命令使用显式 ledger 路径；集成时接收协调器的现有 Ledger/writer，不让生成进程和功能进程各自无锁追加同一文件。若单独运行功能命令需要写原 run 的 ledger，须持有同一个 run 锁；上层已持锁时复用所有权，避免嵌套重复加锁。

实际执行次数、耗时和配置来源必记；本地测试没有 token 使用量，不伪造 LM usage。金额仅按已声明本地计价规则计算，否则标未配置/未知，不能凭空填零。沿用现有单容器资源限制；不新增累计执行次数/总时长额度，缓存命中不记新增执行。无法恢复的中断耗时/费用保持未知。

### 7.4 接入既有 search 路径

按[用户裁定 D06](./验收记录.md#d06)：本节的 holdout 绑定与越权拒绝改为可选加固，不作本期验收门；功能层查询仍按授权与阶段标识核对。

功能评估由命令行入口直接驱动（按 D06 不经 search 调用路径）。本任务只实现功能层；其他层由子任务 05 统一组合。

进入 handler 前校验连接绑定 stage、task 属于当前 view、candidate/prompt/sample 引用属于允许实验；方法只能传不透明样本引用，不能传数据库路径、输出路径或任意代码文件名。当前 evaluate 的早返回要移到成员检查之后，真实功能查询和 cache get 前必须经过相同检查。

按 D06，holdout 的隔离以约定为主：不做锁定状态核对或绑定检查；holdout 结果只进入可信报告、不回流方法，由方法作者遵守。

返回方法的功能反馈是明确白名单中的通过状态、可用性和有界失败原因；不暴露缓存路径、ledger 或完整内部 ExecutionResult。必要反馈字段扩展同步 schema 和检查，不将功能失败误填为静态 hit。

## 8. pass@k 聚合与报告

复用阶段 01 的 `metrics.pass_at_k`，本任务只新增功能记录到逐题 n/c 的适配与输入门：

1. 先检查固定任务集合与明确样本清单完整且唯一；样本身份、模型、温度、提示形态、task/split 和适用版本兼容。缓存读取、重复导入、HTTP 重试或执行 attempt 都不增加独立样本数。
2. 生成失败、空代码及其他有确定 false 结论的样本计入 n、不计 c；true 计入 n 和 c。若预期样本中存在 null、缺行或评估不可用，整体相关 pass@k 输出未定义并列出缺口，不缩小任务集合或把 unknown 填 false。
3. 验证 `k>0`、n/c 是非负整数且 `0<=c<=n`，禁止布尔/字符串强转蒙混过关；每题 n 必须来自经过校验的不同 sample。现有纯公式未覆盖的合法性检查优先加在适配层，不重写估计量。
4. 使用 `1-C(n-c,k)/C(n,k)` 再对固定任务等权聚合；n<k 按 B 未定义。repeats=1 仅能估计 pass@1，不能把同一缓存结果读 5 次得到 pass@5。
5. 输出 MetricResult 的分子、分母、任务/样本数、逐题 n/c、配置和来源，另列通过/不通过/未知、缓存命中/执行数和费用；功能测试完成率与 pass@k 分开命名，不新增 stable_task_rate。

只更新功能层结果/可用性，不重用整份静态 EvaluationRecord 作为功能缓存。与静态层合并时核对 sample/代码哈希，由子任务 05 导出统一报告；重新评估静态/SAST/judge 等仍走 F2 禁用缓存，不因功能命中而跳过它们。

## 10. 实施顺序与集中检查

1. 核对 01/02 交接，建立输入 join 与字节指纹，先用纯数据样例验证来源、身份和状态分类；确定 FunctionalResult、payload 和 local_test 事件字段。

3. 接入 ExecutionSupervisor、内层结果校验、持久归档和 local_test 记账，明确正常不通过与不可用/未完成的区别。
4. 实现阶段 SQLite 缓存及文件发布顺序，验证命中、指纹失配、损坏拒绝和中断恢复，再接入当前集合的 pass@k 重聚合。
5. 接入功能评估入口与 CLI 报告（按 D06 不做越权检查）；向子任务 04/05 交付稳定接口与集中证据。

| --- | --- |
