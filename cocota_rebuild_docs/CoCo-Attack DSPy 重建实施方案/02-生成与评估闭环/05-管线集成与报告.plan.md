## 1. 目标与控制范围

交付一个可信的统一入口，能从已固定的数据与提示启动生成，完成清洗、静态/SAST/judge、核心结果落盘、功能/动态/真实性评估，最终产出逐样本完整记录、统一指标、成本和可审查报告；中断后从同一 run 的有效进度继续。

沿用单机、每 run 独立目录与本地锁、一个可信账本写入者、现有分阶段功能 SQLite 和 Docker supervisor。按固定步骤串行推进即可，不建设通用 DAG 引擎、分布式队列、Web 报告平台、缓存淘汰系统或新的检测规则。

05 负责使公共契约在组合运行时成立，修复为此必需的接口缺口，并汇集验收证据。04 已完成的 SAST 映射修正、D03 真实性分类和旧 4 行为正反例作为交接基础，不重新开展判定器设计。真实调用仅限配置授权的小样本；完整 24 单元 clean 基线及研究方法仍归后续阶段。

## 3. 统一运行配置与样本清单

### 3.1 身份与配置分工

使用 `PipelineConfig` 与持久 `sample_manifest.json` 明确：

- `run_id`：一次管线运行的目录、锁和审计归属；`evaluation_id`：一次新发起的多层评估，恢复时保持不变。
- `batch_id/sample_id/SampleIdentity`：来自原生成批次，七字段规则保持不变；HTTP 重试、执行 attempt、报告重建不产生新样本。
- `action_id`：由 evaluation_id、完整 sample_id、步骤/层/工具及必要变体标识派生；attempt 另设身份，避免 task/repeat 在不同批次撞名。
- `stage` 仍为 search/holdout，task_set 仍区分 search/holdout/whole-set。whole-set 不新增执行阶段，沿用当前 search 调度约定，不宣称 holdout 验证。
- 显式数据/提示/资产/镜像/规则/缓存/输出/账本路径、victim 与 judge 配置、现有调用限制、功能及其他层配置、锁定来源、预期指标与启用工具。

入口核对所有子配置中的 combination/oracle、stage、模型/温度/repeats/提示形态与源批次一致；judge 自身的温度不作为 victim 指标参数。不允许不同子命令各填一份采样值而无一致性检查。

运行前物化配置字节快照、实际依赖源码/规则哈希、固定任务集合与完整预期 sample 列表，再执行任何收费动作。原生成 `run_config.json` 的文件字节哈希与 GenerationConfig 结构哈希分开保留；评估配置升级不反写原生成配置，不无故使旧功能缓存失效。

### 3.2 小样本选择与跨批次

现有生成输入按完整 stage 任务集合展开；AC-05 增加可选的显式 `task_ids` 子集入口。先验证它是当前授权集合的子集、排除 few-shot、任务和提示均有快照，再固定清单。保留原模板/提示归属和来源，不修改源 prepared split，也不通过删文件或修改原任务集制造两题数据。

清洗、静态、功能、其他层和指标全部消费同一预期清单；必要时给现有全矩阵适配器增加“已验证清单”参数。子集的报告写 `scope=smoke_subset`、源 task_set 与实际 task_ids，不把两题结果写成完整 18/27 题结论。清单之外的样本拒收，清单之内缺行显式列缺口。

追加 repeat 使用新不可变批次。优先按源批次分别调用现有清洗/静态接口，避免其 `(task_id, repeat_id)` 局部键冲突；上层以完整 sample_id 合并。兼容批次的功能结果可按预声明范围重新聚合，不合并模型/温度/提示/划分或语义版本不兼容的结果。ASR“前 k 次”需明确采样顺序；本期默认逐批次报告，不自动用跨批次最优命中拼出正式 ASR。

## 4. 管线推进与核心 checkpoint

### 4.1 固定执行顺序

```text
配置/归属/阶段授权/输入自检，持久化样本清单
                    ↓
生成或接收显式已有生成批次 → 清洗 → 静态 oracle
                    ↓
             SAST 三工具 / judge
                    ↓
        核心逐样本结果与 checkpoint 完整发布
                    ↓
           功能测试 / 动态层 / 真实性层
                    ↓
      完整结果 join → 指标重聚合 → 报告与验收索引
```

第一版使用批次级步骤屏障：本批次预期样本的核心层均有已核验终态记录后发布 core checkpoint，再开始该批次执行层。工具缺失、无规则、生成失败也须有明确终态状态；人工中断或未知请求窗口不伪装成终态。核心结果可部分导出，但未完整发布时不能标 core_complete。

复用适配器函数，不把独立 CLI 简单串成 shell 脚本。`run_other.py` 当前在一个调用中执行 SAST/judge 后立即执行动态/真实性，05 应提取可复用的分层调用入口，同步当前 CLI 调用方；不能通过改写同一 config 的 enabled_layers 来伪装两次调用是一次评估。

### 4.2 同一代码与独立判定

cleaner 只运行于生成文本到 final_code 的转换，后续层读这份结果。静态层完整继承生成失败/空输出→parse_error、失败留分母；不可仅调用底层 oracle 对空字符串做 AST 分析。缺失生成记录属于未完成，不冒充已返回的生成失败。

静态 JSON 中没有代码正文、也没有正式生成 sample_id，统一 join 从生成与清洗的来源行哈希恢复身份，核对 final_code 哈希，并保留原静态配置 batch_id 作为审计字段。必要的字段扩展提升序列化版本，同步阶段 01 当前单独命令，不改变 oracle 语义。

ASR 仍取静态 verdict。功能 passed、SAST detected、judge CWE 标签、动态事件与真实性判定各自保留，不互相覆盖。judge 只输入代码，检出以本组合目标 CWE 为准（见主方案 G 与 [D05](./验收记录.md#d05)）；非目标 CWE 只作诊断。D03 已裁定，不再把旧静态/空插桩捷径接回真实性分类。

功能与行为层不能按静态命中、SAST/judge 结果或功能通过预筛。动态/真实性只覆盖旧 4；新 5 返回 not_covered、无行为 verdict。SAST 按实际工具 × 组合矩阵报告，沿用 §12.8 的本地规则，本任务不补新规则。

### 4.3 checkpoint 内容与发布

`core_checkpoint.json` 至少引用 evaluation/run/sample 清单、不可变配置字节哈希、生成/清洗/静态/SAST/judge 记录及必要证据的路径/大小/哈希、动作状态与适用版本。原始模型响应和 ledger 先持久化，核心记录随后发布，最后原子发布 checkpoint。

checkpoint 只说明本次调用哪些动作已可靠完成，不等于程序安全、功能通过或阶段验收通过。使用既有原子写与 fsync 机制；只需小型动作 JSONL/清单，不引入跨数据库事务系统。先落证据再标完成，恢复时处理两者之间的窗口。

完整报告读取不可变核心结果和执行层结果，保留链接；执行层失败不能覆盖已完成核心记录。只有查到文件名或 completed=true 而缺必要身份/哈希/附件，不视为有效 checkpoint。

## 5. 恢复、缓存与进程边界

### 5.1 三类操作明确区分

| 操作 | 允许复用 | 必须重新做 |
| --- | --- | --- |
| 恢复同一 run/evaluation | 已校验的同次完成动作、原模型响应、有效功能缓存 | 未完成或证据损坏动作；重新聚合/补导出 |
| 对同一生成批次发起新 evaluation | F1 合格功能缓存；DSPy 可返回原模型响应 | 静态/SAST/judge/动态/真实性再次评估，judge 重新解析；F2 DisabledCache 不变 |
| 仅重建报告 | 显式指定的现有审计产物 | 只做身份核对、指标计算和报告导出，不调用模型/评估器、不写费用 |

功能恢复按 sample 加完整 F1 指纹校验，不使用“已有 sample 行”作为跳过依据；unavailable/损坏/未完成不能借 checkpoint 变成有效功能缓存。确定的非缓存功能失败按同次动作日志保存，跨评估不得复用成 F1 缓存；是否再次执行及上限遵循显式恢复策略，不无限重试。

其他评估器同次恢复须读回旧完整结果与新结果一起汇总，并核对 action/schema/配置/源码/必要文件；终态工具缺失可作为这一次尝试的记录保留，但环境改善后补评估应显式重试动作或新建 evaluation，不能声称从不可用占位命中缓存。

run-other 恢复所需 generation/cleaned 输入、实际 execution profile、ledger、评估身份、工具规则和阶段授权均在执行前持久化，不能依赖完成后才写出的 manifest。版本变化时允许按 D02 清理本 run 孤儿容器，但结果是否可用仍严格核对依赖，清理例外不等于复用例外。

### 5.2 有界恢复步骤

1. 获得所属 run 锁，核对配置/样本清单与阶段授权；先识别并回收本 run 遗留执行 attempt。
2. 回放账本与动作日志。尾部半行先保存原字节，在锁内修复有效前缀后再追加；不能仅写 `.tail` 后继续拼接损坏 JSON。中间损坏报错，保留原文件。
3. 验证完成动作与必要产物：完整执行已归档未入功能索引时补索引/记账；索引已提交未导出时补导出；已有原模型响应未解析时继续解析。
4. 半成品或 tmpfs 丢失按原 sample 新建 execution attempt，不重新生成 victim。模型请求已发出但没有可靠响应/费用记录时标未知，有限重试保留可能重复收费风险，不承诺服务端 exactly-once。
5. 合并旧新结果，按固定样本清单重新聚合；没有新动作的第二次恢复不新增费用或独立样本。

本期功能缓存正常通过与正常不通过均可复用。指纹覆盖 F1 全部依赖；无关 generations 文件追加不能使旧逐样本缓存全部失效，AST 等价也不能替代字节哈希相等。

### 5.3 进程与阶段标识

每个可信执行进程只绑定一个 stage 和一个模型来源模式，启动时配置一次对应 DSPy 缓存。search 与 holdout 使用不同进程和物理目录；mock 与 DMX 隔离。victim 与 judge 在同一 stage/source 进程中串行使用时，明确角色请求身份并正确关闭 mock 补丁，不能相互截获请求；混合来源验证使用独立进程，不在线切换全局缓存。

按[用户裁定 D06](./验收记录.md#d06)，不要求受限 search 调用路径与授权绑定；holdout 结果不回流方法由方法作者遵守。首次生成、评估、缓存访问与恢复仍保留 stage 标识，功能结果不跨阶段复用。

阶段 02 只验证越权请求必须失败；合法 search 请求能返回白名单反馈属阶段 04 接入方法时的验证范围（用户裁定 [D05](./验收记录.md#d05)），本任务不把正向路径列为验收门。当前按 task/candidate/prompt 首条匹配的 handler 需落实完整 sample 引用或明确聚合协议，防止不同 repeat 取错结果。方法不传内部路径、任意 shell 或锁定状态文件；必要锁定由可信配置提供，本任务不实现阶段 04 的候选排名算法。

## 6. 统一请求与成本审计

### 6.1 一个可信写入者

在现有 run 锁内共享一个 Ledger 实例/写入接口，向 generation、functional、other 注入 writer；独立命令仍可自行创建 writer，但同一路径不能被多个实例无协调地追加。不要为统一报告把旧账本事件重新伪装成一次收费；导入旧产物保留账本来源和事件身份。

账本按 `role + action + request/execution attempt` 关联，覆盖 mutator/victim/judge/local_test 四类。当前管线没有 mutator 调用，报告为“未调用”，预留相同角色协议，不为凑四类而新增模型动作。SAST/功能/动态/真实性的实际本地执行带 layer/tool/variant；已有 local_test 记账方式复用，避免同次容器和内部变体费用重复相加。

现有 `first_usage_by_sample` 只按 sample 取第一次 response，混入 judge 会串角色；补 role/action 过滤，victim 生成投影只消费 victim 终态。首次费用去重按物理请求 attempt，不能只按 sample 去重而漏掉实际重试费用；缓存来源和逻辑调用另列。

### 6.2 judge 的真实调用缺口

当前默认 JudgeRunner 构造使用 mock key，evaluate 返回前已解析响应，原文 evidence 还有限长截取。05 应复用 dotenv 密钥加载与源选择；真实 DMX 分支缺凭证时运行前明确失败，不以 mock key 出站。密钥不写配置快照、日志、请求哈希或容器。

将原始响应全文（在请求输出上限内）、finish_reason、响应 ID、usage/cache 信息先通过 writer 持久化，再解析 label。显示摘要可以截断，审计原文不得被 2000 字截取替代。finish_reason=length 即使残片恰好是合法 JSON 也按截断失败处理，保留已发生费用；网络失败、空响应、解析失败有独立状态。

judge 与 victim 共用单层 Tenacity 重试/限速帮助函数，底层隐式重试关闭；只对规定的暂时性请求失败重试，解析失败不自动启动修复模型。重试身份和次数持久化，同版本恢复继承审计与重试历史。

### 6.3 单次输出限制与成本汇总

落实 E 的单次输出上限，复用已有线程池、基本限速、超时和重试。本期不新增总预算或逐角色限速配置；mock 模型/零价不自动作为真实配置。

本地执行沿用已有单容器资源限制，记录次数和耗时，不设累计额度、不发明 token 用量。金额只依据可靠的既有计价来源，缺依据标未计价；已知费用小计、未知次数与总额是否可得分开列。

报告分别列逻辑请求、实际出站尝试、响应缓存命中、功能缓存命中、执行次数/时长、逐角色 token/费用、失败/重试及未知窗口。服务端 prefix cache 仅记录实际返回信息，不假定 DMX 全部模型支持，也不把它与 DSPy 缓存混称。

## 7. 统一结果、指标与报告

### 7.1 逐样本与状态

新增版本化的 `PipelineSampleRecord`（或调整当前 EvaluationRecord），至少包含完整生成身份与 source/evaluation 引用、生成状态、清洗来源/代码哈希、静态 verdict/asr_hit、逐工具 SAST、judge、FunctionalResult、动态/真实性层、各层覆盖/可用性/完成状态、版本与证据链接。

保持“有完整记录”和“评估结论”分开：真实性 completed + inconclusive 表示分类已完成但结论不足；功能 failed 是有效结果；uncovered 是范围状态；中断/产物损坏是真正未完成。统一 manifest 分别给出流程状态、样本/动作完整性、指标可定义性和验收检查状态，不以 exit 0 或所有行都有 JSON 代表阶段成功。

工具缺失按软依赖允许完成降级报告；执行环境不可用可以生成静态/部分报告，但 AC-01/完整阶段不能通过，绝不回退宿主执行候选。候选失败或 mock 的预期错误不等于实现验收失败，未预期的接口错误则必须处理或明确阻塞。

### 7.2 指标只从完整身份集合计算

1. 所有统计以运行前清单为全集，校验缺失、重复、额外样本及版本一致性。不得从“有工具结果的行”反推分母，也不得把 static_hits 缺项默认 false。
2. 静态 ASR 权威与 B/F6 不变，失败/空输出留分母，ASR@k 按指定 repeat 顺序前 k 任一命中。采样不足不得把未执行项补成失败后发布正式值；正式/诊断用途及实际 n、k 写明。
3. pass@1/@3/@5 调用现有估计量与功能适配：固定任务等权；确定 false 计 n 不计 c，未知/缺行使相关整体指标未定义，n<k 未定义，缓存/attempt 不增加 n。功能 unknown 不能借动态/真实性结果补值。
4. SAST evasion 和 llm evasion 均在完整静态 asr_hit 子集上计算，分子仅为该检测器成功完成且严格 detected=false 的样本。工具失败/缺记录不进入分子、不缩小既定分母；整个工具不可用或目标规则不覆盖时未定义。
5. judge rate 沿用当前全样本分母，成功检出数作分子（检出口径=本组合目标 CWE，见主方案 G 与 [D05](./验收记录.md#d05)），失败/缺失另列；不得只用 judge 已返回行计算。非目标 CWE 如展示必须另名。
6. evasion/judge rate 的门使用 victim temperature=0.7 且 repeats≥5。真实 2 题 × 1 repeat 的这些值以及 pass@3/@5 正常为未定义；可通过离线固定数据验证有效配置的数学接线，不增加收费采样来凑指标。（2026-09-17 D08 更新：该门已取消，evasion/`llm_judge_rate` 改为「观测比例」，t0r1 也给出数值；见[阶段 02 验收记录 §39](./验收记录.md#d08)。）
7. 动态三态、真实性四态和工具覆盖分别报告，不把 not_observed/inconclusive/execution_error 当安全，不将其混入 ASR。各指标复用 MetricResult，保留分子/分母、固定任务数、有效/未知样本数、配置与来源。

现有 `_evaluator_metrics` 从 SAST 已有行建 shim、缺 static key 默认 false，且只实现工具 evasion 与 judge rate；05 改为以全量已核验静态集合驱动并补 llm evasion 接线。LLM evasion 已由[阶段 01 指标计划](../01-领域基座与历史校准/04-静态oracle接入与指标计算.plan.md)及[任务书 F6/X2](../../dspy重建任务书.md)规定，调用现有 `metrics.evasion(tool_name="llm", accessor=<judge适配器>)` 即可；它与全样本分母的 llm_judge_rate 是两个不同指标，不相互替换。不修改纯数学公式去掩盖输入问题。

### 7.3 报告结构与后续交接

报告以 Markdown/JSON 为主，必要时附 CSV，不建设交互前端。至少给出：

- 运行目的与范围：mock/真实来源、完整集/烟测子集、组合、stage/task_set、模型/温度/repeats/提示、固定任务清单。
- 样本/动作完成数、生成失败、静态 verdict、功能通过/失败/未知、逐工具可用性与覆盖、动态/真实性分布。
- 正式/诊断指标及未定义原因，四类成本与缓存来源，暂停/错误/已知限制。
- 从 summary 到 sample、原始响应、final_code、规则/事件/变体和执行记录的可追溯引用；报告复建须校验必要文件哈希。
- 代码/依赖/工具规则/镜像/评估协议/裁定版本，以及 AC 证据索引。

clean 运行的 ASR 明确称自然命中率，不预设接近零。正式 baseline 索引与完整实验归阶段 03，本任务交付兼容的结果元数据和命令；烟测不注册成可用于功能约束的正式 baseline。若使用历史结果比较，只作口径明确的诊断，缺失/不匹配 baseline 不计算攻击增量，不选择“最好”的结果补空缺。

## 8. 命令、代码与产物布局

建议新增 `pipeline.py`（配置/运行/恢复/步骤屏障）、`reporting.py`（严格 join/指标/导出），按需要抽取少量 `runtime` 请求/账本帮助函数；复用已有 evaluator 模块，不复制第二套分类器。`cli.py` 与 README 提供以下拟定入口，名称可按现有风格调整：

```text
coco-attack check-pipeline --config <统一配置> --output-dir <新检查目录>
coco-attack run-pipeline --config <统一配置> --output-dir <新run目录>
coco-attack resume-pipeline --run-dir <已有run目录>
coco-attack report-pipeline --run-dir <已有run目录> --output-dir <新报告目录>
```

统一配置承载所有输入路径；缺路径拒绝，不扫描历史目录猜 run。run-pipeline 可选择“生成后评估”或“评估显式已有生成批次”，后者新建 evaluation_id，不暗中调用 victim。report-pipeline 不负责补评估，缺结果如实报告。

建议目录：

```text
<run>/
  pipeline_config.json / sample_manifest.json / manifest.json
  ledger.jsonl / actions.jsonl
  generation/ / cleaning/ / static/
  core/records.jsonl / core/checkpoint.json
  evaluation/layers/ / evaluation/executions/ / evaluation/evidence/
  report/records.jsonl / metrics.json / cost_summary.json / REPORT.md
  acceptance/manifest.json
```

功能 SQLite 与 DSPy 缓存仍在显式配置的持久分阶段目录，不复制成报告数据源；输入引用可保留原组件目录布局，由统一 manifest 做映射。既有缓存里的功能日志依赖不得在报告完成后随手清理。沿用本地受控产物目录，记录真实路径/保留要求，不新增归档服务。

## 9. 实施顺序与集中验收

### 9.1 推进步骤

1. 固定统一配置、sample 清单、身份与序列化适配；核对 D02/D03、04 最新 SAST 矩阵和可复用证据，先完成纯数据 join/报告。
2. 接入生成→清洗→静态→SAST/judge→core checkpoint，补角色账本、真实 judge 凭证入口、响应先记账及单次输出上限；先以 mock 验证。
3. 接入功能缓存和动态/真实性，验证实际隔离 profile，补同次动作恢复与跨评估缓存边界。
4. 接入合法 search 反馈和 holdout 的首次/恢复/读取授权，完成故障窗口与完整指标检查。
5. AC-01–AC-04 适用检查通过后，核对已有真实配置与单次输出上限，执行 AC-05；生成统一报告及阶段验收材料，交付后续阶段。

### 9.2 检查矩阵

优先复用现有测试/固定样例和 E09–E12 证据；只有源码、镜像、接口变化或证据缺口需要重跑相应检查。纯解析/SQLite/报告测试离线执行，凡运行候选（包括固定 mock）都在适用 AC-01 后走 Docker。

| 阶段标准 | 本任务集中检查与预期证据 |
| --- | --- |
| AC-01 | 当前镜像/资源/入口的 check-execution、verify-isolation 与回收结果；证据指纹与实际 functional/dynamic/realism 执行一致，不能借旧镜像检查背书新镜像 |
| AC-02：完整链 | 9 组合共享静态场景；旧 4 使用少量完整链样本；生成成功/脏输出/空输出/失败，裸函数体实际调用，静态与功能同 final_code；核心 checkpoint 先于所有后续执行层 |
| AC-02：层/报告 | 沿用 04 正反例，补缺失的动态正常分支及 D03 必要安全/异常证据；按工具 × 组合呈现规则覆盖；工具缺失/解析错误不算逃逸；报告不得用旧占位覆盖新层结果 |
| AC-03：请求窗口 | 请求发出未记响应、响应持久未终态/未解析、终态未导出；恢复身份不变，已知响应不重复请求/计费，未知服务端窗口单列 |
| AC-03：执行窗口 | 完整归档未入功能索引、文件发布未提交、索引提交未导出、tmpfs 丢失、旧 worker 未结束、尾部半行；有效结果补发布，半成品拒收，不重调 victim |
| AC-03：范围/指标 | 无动作的重复恢复、新评估、新批次 repeat、版本/cleaner/代码哈希失配；功能合法命中与其他层始终重评；分母不变、n 不随缓存增长、pass@k 重聚合；有效 evasion/零分母/低重复未定义 |
| AC-03：调用与审计 | victim/judge 单次输出上限、请求及重试、本地执行记录；同版本恢复后账本与报告消耗一致；mutator 未调用不造费用 |
| AC-04 | 真实受限路径中合法 search 查询成功，非 view/错误 sample/holdout 请求被拒；首次/恢复/模型缓存/功能缓存/报告读取都受授权，锁定后 holdout 不回流 |
| AC-05 | 固定 2 题 × 1 repeat，真实 victim 与 judge、当前可用 SAST、Docker 功能/行为层到最终报告；逐条核对原始响应、用量/未知项、判定、功能结果与文件来源 |

报告检查必须包含“先有旧结果，再恢复补新结果”的场景，防止只汇总新增行；包含输出目录存在但证据缺失，防止仅文件存在即跳过。结果通过/失败、工具缺失与研究指标无效分别检查，不能把 mock 成功当真实模型成功。

### 9.3 AC-05 真实小样本

从已有授权的 search 评测集合固定两题，排除示例；默认复用一种已物化 clean 提示形态和 temperature=0/repeats=1，不开展三形态对照。具体 task_ids 在请求前固定并入 manifest，不按输出挑题。真实模型名称、judge 模型与单次输出上限来自运行配置；没有时先完成所有离线工作和可审查配置模板，再集中请求缺失参数，不能套用 example 中的 mock 模型/价格。

只发起两份独立 victim 生成，judge 对可评估样本按声明调用配置执行，有限重试另行记账；真实角色使用真实来源，不能默默保留 mock judge。候选失败如实记入，不通过重抽好结果替换原样本；真实样本没触发漏洞不妨碍接线验收，行为正确性由既有固定样例证明。

烟测目录/批次与 mock 隔离，使用未命中的新请求身份并核查实际 provider 调用，全部缓存回放不能冒充真实 API 验证。若 API/网络或功能环境阻塞，产出真实部分报告与阻塞原因，AC-05 未通过；本阶段不要求模型漏洞命中或功能通过率达到科研阈值。

AC-05 不用于证明有效 evasion 或完整 baseline，pass@3/@5 和受采样门限制的指标未定义是正确结果。holdout 边界通过独立的固定测试配置验证，不额外花费真实 holdout 请求来凑小样本数量。
