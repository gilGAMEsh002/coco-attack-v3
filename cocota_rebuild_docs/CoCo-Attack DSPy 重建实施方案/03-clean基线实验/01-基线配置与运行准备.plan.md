## 1. 目标与控制范围

交付一个可审查的基线根目录：固定的数据/提示输入快照、逐单元运行清单、每单元 pipeline 配置、锁定记录和启动条件核对结论，使子任务 02 可以不依赖任何人工临时决定直接执行。

具体边界：

- 运行清单与配置生成由新增的最小编排模块完成（用户已裁定采用此方式）；本任务交付矩阵定义、配置生成、清单登记与锁定部分，执行循环与恢复归子任务 02，索引与分组报告归子任务 03。
- 不修改阶段 01/02 已验收的 pipeline、评估器、oracle 与提示素材；发现差异先整体汇报，由用户裁定。
- 不实现累计预算、共享额度或请求总量准入（[D04](../02-生成与评估闭环/验收记录.md#d04)）；只核对并记录单次输出上限与既有调用限制。
- victim 模型、judge 模型、单次输出上限、执行镜像摘要、计价参数等运行取值均由矩阵配置提供，本计划不预写具体值；1,962 次请求是核对基准，不是费用授权。

## 3. 基线根目录与固定输入快照

拟定布局（目录名可按现有风格微调）：

```text
<baseline_root>/
  matrix-config.json            # 本任务输入：必填模型/限制/路径
  inputs/data/                  # prepare-data --combination all 输出
  inputs/prompts/               # materialize-prompts 4 组合 × 3 形态输出
  inputs/asset_manifest.json    # 资产清单引用与关键哈希摘录
  manifest/run-manifest.json    # 运行清单（本任务创建，02/03 更新状态）
  units/<unit_id>/<stage>/      # 每单元 pipeline run 目录（02 填充）
  cache/functional/             # 共享功能测试缓存根；实际落盘 functional-cache-v1/<stage>/
  reports/                      # 03 的分组报告与审查材料
  index/baseline_index.json     # 03 的 baseline 索引
```

输入快照要求：

1. `prepare-data` 与 `materialize-prompts` 在同一干净工作树下执行，记录 git commit、DSPy 版本、数据契约 `bigcodebench-screened-v1`、`prompt-materialize-v1`/prompt version `1`、`cleaner-v3`、oracle 版本（cwe078-0 为 v2 并记录源码哈希，其余复用原件）、`static-shell-v1`、划分算法 `sha256-seed-taskid-v1`、执行镜像摘要与 harness 版本、`judge_prompt_version` 与 `judge_detection_version`。
2. 核对评测题数：cwe078-0 27（含任务 205，依[阶段 01 D02](../01-领域基座与历史校准/验收记录.md#d02)）、cwe094-0 4、cwe295-0 33、cwe502-0 45；基线为整组合运行，各组合 `split.json` 应为 whole-set 且与 `configs/splits.baseline.json` 一致。`configs/splits.json` 的 cwe078 18/9 属方法阶段，不用于本基线。题数不符即停止准备，按[差异处理 C](<../CoCo-Attack%20DSPy%20重建实施方案.md#calibration>)整体汇报，不擅自调整集合。
3. 每形态 `prompt_hashes`、few-shot 示例 ID（4 个，与评测集互斥）、`attack_config.enabled=false` 逐项核验；0-shot 与 few-shot 使用相同评测集合。
4. 输入快照只读化后供全部单元引用；任何重新物化视为新快照，触发受影响单元重核，不静默覆盖。

## 4. 实验矩阵与运行清单

### 4.1 矩阵定义

`matrix-config.json` 必填字段：victim 模型、judge 模型、单次输出上限 `max_tokens`、执行镜像摘要、基线根目录、资产/配置路径。可选字段：既有调用限制（RPM/TPM、超时）、重试上限、并发度（默认 1=串行）、计价参数（输入/输出价格、币种、`pricing_version`，缺省则成本记未知）、`enabled_layers`、`sast_tools`、judge 开关。一份矩阵配置只含一个 victim 模型；第二个模型另起矩阵与基线根目录，符合 F 的不可变批次要求。

默认启用层 = 静态 + SAST + judge（`enabled_layers=["sast","judge"]`、`sast_tools=["bandit","semgrep","codeql"]`，judge 默认启用）；dynamic/realism 默认关闭、可配置开启。functional 是 pipeline 固定步骤、始终执行，不属于 `enabled_layers`。

矩阵固定为 4 组合 × 3 形态（`clean_0shot`、`clean_fewshot_no_cot`、`clean_fewshot_cot`）× 2 采样配置（temperature=0/repeats=1；temperature=0.7/repeats=5），不增删单元。

### 4.2 请求数核对

每单元 victim 请求数 = 题数 × repeats；四组合均为整组合单次运行（cwe078 的 27 题一次跑），请求数按题数计一次，不另乘阶段数。

| 组合     | 题数 | t0r1（×3 形态） | t0.7r5（×3 形态） |            小计 |
| -------- | ---: | ---------------: | -----------------: | --------------: |
| cwe078-0 |   27 |               81 |                405 |             486 |
| cwe094-0 |    4 |               12 |                 60 |              72 |
| cwe295-0 |   33 |               99 |                495 |             594 |
| cwe502-0 |   45 |              135 |                675 |             810 |
| 合计     |      |                  |                    | **1,962** |

合计与主方案 H 的 1,962 估算一致，作为逐单元预期请求数与运行后实际请求数的核对基准；不含 judge 与重试，不构成费用授权。注意 1,962 是 victim 请求数，与 24 次 pipeline 运行是不同的计数：一次运行内的请求数 = 该组合整组合题数 × repeats。实际请求数（含重试、缓存命中来源）由 02 从 ledger 汇总，与本表差异超出重试可解释范围时列入异常。

### 4.3 运行清单 schema（run-manifest-v1）

每单元登记：`unit_id`（建议 `<combination_id>__<form>__t<temp>r<repeats>`）、`combination_id/oracle_id/form`、`split_mode`（基线为 `whole-set`）、运行条目（每单元一条，内部 `stage="search"`，对外口径以 `split_mode` 为准）、任务集合与 ID 列表哈希、预期题数与预期样本数（题数 × repeats）、采样配置、`batch_id`、victim/judge 模型与 `max_tokens`、启用层与 SAST 工具、版本指纹集（§3.1）、功能缓存根、unit 状态（`pending/configured/running/complete/incomplete/blocked`；`locked` 为方法阶段保留、基线不用）、run 目录与 config 路径、`lock_ref`（整组合基线恒为 `null`）、已知限制。

清单在发起任何收费请求前完整持久化；02 逐单元更新状态与产物位置，03 据此核对覆盖。单元之外的样本拒收，单元之内缺行显式列缺口（沿用阶段 02 的清单语义）。

## 5. 锁定规则与启动条件

### 5.1 无基线 holdout 锁定

- clean 基线按整组合测量（Z）：四组合各 1 次运行，不存在基线 holdout，也不生成 `baseline-lock.json`；`prepare-baseline`/`check-baseline` 不再要求 cwe078 为 search_holdout，改用独立整组合配置 `configs/splits.baseline.json`。
- 18/9 划分属于方法阶段；基线的 holdout 结论只能由索引的**派生 split 视图**给出（cwe078 从同一次整组合运行切出 `search-18` / `holdout-9`），**不得把整组合数字当作 holdout 结果**。
- 研究有效性规则保留在方法阶段：阶段 04 的方法不得按 holdout 结果选择或修改模板/形态；阶段 02 D06 的阶段隔离仍为约定（不做代码强制）。

### 5.2 启动条件核对（check 级，不收费）

1. Docker 可用、`check-execution` 通过、执行镜像摘要与清单指纹一致；Docker 不可用时可以完成配置准备，但须在清单标注功能测试将不可用、相关单元不得宣称可用功能基线。
2. `check-evaluators` 记录启用层（默认 SAST 三工具 + judge）的可用性；工具缺失/失败按组合 × 工具列入已知限制——该工具 evasion 未定义、失败样本不进 evasion/judge rate 分母，不等于未检出（[阶段 02 D08](../02-生成与评估闭环/验收记录.md#d08)）。
3. `.env` 存在且含 `DMX_API_KEY`（只核对存在性，不记录密钥）；DMX base 固定 `https://www.dmxapi.cn/v1`。
4. 每单元 `check-pipeline` 通过；`task_ids` 烟测子集入口不得用于正式单元。
5. 版本冻结口径：同一版本 = 代码提交 + 输入快照哈希 + 评估版本三元组，写入清单。基线提交后仅文档改动不影响基线版本；工作树存在代码改动须先提交或经用户裁定。

## 6. 编排模块的本任务部分（拟定实现）

新增 `coco_attack/experiments/` 包（名称可按现有风格调整），本任务实现：

- `matrix.py`：读取 matrix-config，展开 24 单元/24 运行条目，校验组合注册表、形态、划分与预期题数。
- `manifest.py`：run-manifest-v1 的创建、原子更新与校验；状态机只允许 §4.3 列举值。
- `configgen.py`：为每单元生成 `PipelineConfig` JSON（含共享功能缓存根、显式模型与 `max_tokens`、正确 stage、来源 `dmx`、`enabled_layers`/`sast_tools`/judge 开关），并输出 `check-pipeline` 批量核对入口。
- CLI：`coco-attack prepare-baseline --matrix-config <cfg> --output-dir <baseline_root>`（建目录、物化输入、生成清单与配置）、`coco-attack check-baseline --baseline-root <dir>`（§5.2 全项核对，报告各单元启用层与工具可用性）。

单元调用方式与子任务 02 §7 保持一致：每单元一次独立子进程。执行循环、恢复与索引分别在 02、03 的 plan 中定义；模块只复用现有 pipeline/评估入口，不复制第二套评估逻辑。
