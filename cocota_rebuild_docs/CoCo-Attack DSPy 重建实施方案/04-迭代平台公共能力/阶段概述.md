# 阶段 04：迭代平台公共能力

依据：[主实施方案](../../CoCo-Attack%20DSPy%20重建实施方案.md)工作包 I，并复用工作包 E、F 的服务；需求对应 F8、E1、E4、X1–X3。状态：规划阶段，尚未实施或验收。

## 1. 阶段目标与边界

在已验收的生成、评估与基线之上提供可插拔方法所需的公共执行服务，使方法能够登记候选、请求生成/评估/纯推理、获得受限反馈、查询预算、持久化计划并按协议锁定结果。

本阶段不确定具体研究算法，不引入 DSPy 优化器，不固定选父、变异、反思、停止或多目标合成策略。以两个确定性测试驱动验证平台能力；它们不是研究方法，不能用来宣称完成任务书的两种真实方法对照。

## 2. 输入与依赖

- 阶段 01 的任务、候选提示、归属和版本约定；阶段 02 的生成/评估服务、阶段隔离、ledger、DSPy 响应缓存和功能测试缓存。
- 阶段 03 的 baseline 索引、配置与口径、功能通过率和自然命中率，用于校验功能约束与增量比较的可用性。
- 真实方法运行前需显式提供目标、功能指标 P、ε、baseline 选择、增量条件、锁定聚合规则及预算；平台不自行补充科研参数。测试驱动可使用明确标注的固定测试配置。
- 仅 cwe078 已有 18/9 划分实例；其他组合若尚未配置 holdout，不能自动获得三条件成功判定，只能报告对应 whole-set 事实与缺失条件。

## 3. 子任务与推进顺序

| 子任务 plan | 主要工作与责任边界 | 依赖与交付 |
|---|---|---|
| `01-方法接入与执行服务.plan.md` | 最小插件入口、候选登记、生成/评估/纯推理服务、search 受限视图，接入两个测试驱动 | 依赖阶段 01–03 公共接口；交付平台服务边界与测试驱动 |
| `02-计划持久化与预算审计.plan.md` | 计划先落盘、稳定动作身份、动作恢复、四类预算、候选来源与字段差分记录 | 依赖 01；复用阶段 02 ledger 与缓存，交付可恢复运行记录和预算账本 |
| `03-反馈边界与锁定协议.plan.md` | 按阶段过滤反馈、校验 baseline、执行预固定锁定与成功判定，集中验证平台 | 依赖 01、02；交付锁定记录、隔离检查和平台验收报告 |

先明确服务边界和数据投影，再细化持久化与锁定。子任务 plan 只约束运行时对外能力，不把一种历史方法内部流程写成所有方法必须遵循的接口。

## 4. 公共契约与交付物

### 服务边界

- 最小方法入口接收方法配置、恢复状态和 search 服务句柄；方法不直接访问 runner 路径、holdout 空间、凭证或 Docker socket。
- 候选登记保留候选/模板哈希、父代、实际字段差分、状态与原因；提示版本改变后遵守产物失效规则。
- 纯推理动作可以产生反思或计划而不创建候选，仍走模型调用、预算和审计服务。
- 生成/评估服务沿用阶段 02 的权限、采样和缓存规则；只缓存功能测试结果，其他评估缓存继续仅保留接口，不在本阶段扩展范围。

### 持久化与预算

- 含模型参与的计划必须先完整持久化再执行；动作身份稳定，恢复继续未完成动作，不重新规划替代已有计划。
- 预算分 mutator、victim、judge、本地测试四类；失败、重试、修复和被淘汰候选纳入成本。首次响应即记账，缓存与恢复不重复累计，无法确认的成本明确标未知。
- 实验记录保留模板来源、分母、版本、预算与保留/淘汰原因；设计假设、代码实现、运行观测、实验结论分别记录。
- 相同候选是否复用既有样本由运行前协议决定；允许复用时保存来源，不增加独立样本数。

### 反馈、锁定与成功判定

- 反馈同时包含命中与失败信息，并严格过滤方法当前阶段声明不可见的字段；命中反馈也不得绕过字段权限。
- 复用阶段 02 的物理隔离和可信协调器：锁定前拒绝 holdout 请求/读取，锁定后的结果不回流方法；阶段 04 验证实际方法入口无法绕开边界。
- 锁定规则文件先于运行存在，其 hash 写入 manifest。扫描全部功能合格候选，按预固定规则选最高者，平分按候选哈希排序；逐任务频次/前沿仅可用于方法选父。
- 全部候选不合格时输出“未找到可行解”，不返回未过门禁模板；baseline 不可用或口径错配时不能认定候选功能合格。
- 成功判定按方法预设目标实例化，使用相应 search/holdout 增量与功能约束；平台不自行决定多个目标的优先级。条件缺失时报告无法判定，不伪造成功。

阶段最终交付为公共服务、方法接入示例、持久化与预算记录、受限反馈、锁定/结果报告，以及两个明确标注用途的测试驱动。

## 5. 阶段统一测试与人工验收

沿用前阶段的生成、评估、隔离和缓存检查，仅补运行时新增行为。用两个确定性驱动和少量共享场景集中覆盖协议，不为每项服务分别建设完整测试套件。

| 验收组 | 集中场景与证据 |
|---|---|
| 方法接入与纯推理 | 两个驱动使用不同调用顺序，均能登记/评估候选；不产生候选的推理动作可完成并记账，无需改数据或评估层 |
| 动作恢复与预算 | 动作中途 kill 后恢复，不重新规划，不重复计算已完成动作成本；失败、重试和淘汰可追溯 |
| 反馈与 holdout | 一组越权请求覆盖禁用反馈字段、锁定前 holdout 访问及锁定后反馈回流，均被拒绝；合法命中信息仍可见 |
| 锁定与结果 | 全量功能合格候选排序、平分规则、全失败、baseline 错配、不同目标配置与缺失成功条件 |

轨迹一致性优先用确定性 mock 或固定 DSPy 缓存重放验证；真实 API 即使 temperature=0 也不作为服务端绝对确定性的承诺。记录动作序列、输入输出引用、成本和恢复位置作为证据。

统一汇总到[验收记录](./验收记录.md)：服务完成情况、协议测试结果、测试驱动产物、人工审查结论和未决问题。既有领域判定出现差异仍先上报，不借平台实现改变语义。

## 6. 完成条件与后续衔接

公共服务可被两个测试驱动使用，恢复、预算、阶段边界、锁定及全失败处理通过集中验收，且文档明确科研参数和能力限制后，可将本阶段标为完成。

后续每种研究方法单独制定 plan，决定内部算法与实验配置，并在本平台上实施真实对照。本阶段不自动启动付费方法实验，不将平台测试结果写成攻击效果或方法优劣结论。
