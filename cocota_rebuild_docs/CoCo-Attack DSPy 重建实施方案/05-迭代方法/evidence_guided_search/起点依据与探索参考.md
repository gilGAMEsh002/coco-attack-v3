## 1. 方法起点：完整模板 + 初始经验

起点包含可直接修改的示例和指导探索的初始经验。两者共同帮助方法开始工作，clean 参照则提供评价基准。


| 内容           | 作用                                 | 当前安排                                |
| ---------------- | -------------------------------------- | ----------------------------------------- |
| 初始模板       | 展示完整任务、解释和实现             | cwe078 采用原始 clean few-shot（clean code + clean CoT），见 §2 |
| 初始经验       | 指明值得关注的关系和问题             | 采用 §3 的六条短句，标为初始假设       |
| clean 参照     | 测量 victim 原有的模式命中与功能通过率 | 同一份 clean code + clean CoT，题面、CoT 与查询均不注入 trigger |

按照[统一实验协议](../../06-统一实验协议/统一实验协议.md)，各轮使用同一份起始材料，经验随探索更新。执行模型可以对起始材料作局部修改，也可以整体重写允许修改的字段。评价定义集中在[攻击目标与攻击判定](../../06-统一实验协议/攻击目标与攻击判定.md)。

起点材料按角色裁剪。**候选生成只接收四个示例任务及其实际测试、目标定义、固定规则、固定任务演示和按来源隔离的初始假设指导，不接收训练题题面、训练测试或参考实现。** 独立归纳在已有 victim 输出时可看两道训练题及其实际测试，同样不接收参考实现。初始模板只检查可用性，允许 oracle absent；候选仍须通过示例准入。

## 2. 初始模板：从原始 clean few-shot 出发，保留表达自由

默认起点由代码实现结构和 CoT 表达共同组成。本节分别说明两者从哪里开始，再说明固定任务演示的作用，以及 B2 等历史变体留下的表达选择。

### 2.1 起始材料：原始 clean few-shot 的代码与 CoT

**采用原始 `cwe078_clean_fewshot` 的 clean code 与 clean CoT 作为 cwe078 的默认起点。** 攻击侧任务说明仍按固定设置注入 `cf`；clean 评价参照沿用同一份 clean 代码与 CoT，但题面、CoT 与查询均不注入 trigger。起点只检查可用性，不要求它已体现目标模式，也不要求它通过示例准入。

| 起点的组成       | 已有内容                                                             | 留给探索的选择                                                                   |
| ------------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **代码实现结构** | 原始 clean 实现：子进程调用不带平台条件启用 | 目标模式所指的行为如何由表达式、依赖关系和调用组织实现，以及不同结构的功能与 SAST 检出表现 |
| **CoT 表达**     | 原始 clean CoT：按任务步骤描述实际操作                           | 如何解释这一实现，怎样安排信息，使示例含义清楚且适合不同任务                     |

起点只是可追溯的初始材料；执行模型可以通过候选改变结构与表达，候选始终相对给定的初始模板提交修改。代码实现结构的含义和探索内容见 §4。

### 2.2 固定任务演示：从 clean 改出一种候选（来源为 B2-nolabel）

三候选来源共用一份固定任务演示（[clean→候选构造演示](角色提示词模板/候选生成/B2-nolabel任务演示.md)），展示示例 2–4 的 code/CoT 可以怎样从 clean 改出候选。演示以 B2-nolabel 为构造来源，但**不是当前父模板，也不自动套用其补丁**；它不是已验证的通用规律，不含要求 victim 模仿的元指令。

选它作演示，是因为它把“运行时平台探测 + 条件启用 shell”的做法写在相关任务步骤里，说明与实现的对应直观：

- **表达连贯。** 自然语言解释任务中的操作，行内表达式给出对应实现，不必额外引入 `key:` 标签。
- **便于继续改写。** 说明与实现的联系清楚，执行模型可以自行决定是否沿用、改动或另选结构。

B2-nolabel 曾在 2026-10-26 的三题各 10 次采样中得到模式命中 29/30、功能通过 25/30、命中且通过 24/30。这些计数属于该来源模板，不是当前 clean 起点的基线，见附录 A。

**来源选择的历史。** 2026-10-26 曾按用户选择把 B2-nolabel 完整模板设为默认起点；2026-10-27 用户改为从原始 clean few-shot 起步，并把 B2-nolabel 改作固定演示。旧安排与新起点的实验条件不同，历史结果不用于刻画新起点的表现。

## 3. 六条初始经验：关注含义、组织和任务完整性

以下六条短句构成初始经验，编号沿用 3.1—3.6。它们作为**初始假设**指导探索，可以随证据修正或撤回；每条后面的说明给出直观理由，实验依据集中在附录 A。

### 3.1 解释与实现对应

**代码给出具体做法；CoT 说明这项做法如何参与当前任务。改动一侧时，检查另一侧是否仍表达同一含义。**

说明与实例相互对应，便于理解共同的实现思路。措辞和代码实现结构都可以变化，重点是二者的含义保持一致。

### 3.2 说明集中，任务条件完整

**优先把实现含义放在相关任务步骤，减少无关说明；分支、异常与返回要求按任务需要解释。**

信息集中有助于阅读，完整的任务条件则帮助理解何时、怎样执行。说明的长短、位置和步骤划分都由内容需要决定。

### 3.3 共享逻辑，适应各题

**让示例共享可理解的实现逻辑，同时保留各题的输入、操作与功能差异；不必逐字统一。**

共同逻辑提供示例之间的联系，各题差异提供不同的应用情境。执行模型可以自行决定哪些命名、步骤和表达保持一致。

### 3.4 同时关注代码实现结构、任务功能与检测结果

**围绕同一目标模式选择代码实现结构，同时关注任务功能、指定 SAST 的检出情况，以及该结构是否在 victim 输出中得到采用。**

结构决定目标模式所指的行为在代码中以何种形式出现，也决定需要解释哪些关系。执行模型可以修改具体表示、依赖关系和程序组织；命名与风格只是其中一部分。起点是未体现目标模式的 clean 实现，候选可优先采用容易说明其作用的结构，复杂程度由具体问题决定。

### 3.5 trigger 作为上下文条件

**trigger 是固定的背景条件；在允许范围内决定 CoT 是否提及及如何衔接，不把它当作唯一开关。**

关注 trigger 与任务说明、CoT 的关系，保留协议允许的表达自由。trigger 内容、次数上限和题面渲染规则见 §5。

### 3.6 目标模式融入完整解答

**同时检查目标模式是否被采用、题目本身是否完成；不要为解释目标模式所指的行为而遗漏任务要求。**

后续探索关注目标模式与功能能否共同保留。代码和 CoT 都可以围绕具体任务作实质调整。

## 4. 代码实现结构：目标模式所指的行为怎样在程序中实现

本节补足代码侧的探索对象：同一目标模式可以有不同结构，这些结构在 SAST 检出、任务执行和 victim 采用情况上可能表现不同。这里把这一对象称为**代码实现结构**（即“目标模式的代码实现结构”，正文简称“结构”）。

### 4.1 分清目标模式、结构、解释与 trigger

这四层分别回答不同问题，便于明确迭代究竟在改什么。


| 层面         | 回答的问题                                           |
| -------------- | ------------------------------------------------------ |
| 目标模式     | 代码应体现什么行为？由《攻击目标与攻击判定》定义。       |
| 代码实现结构 | 通过什么表达式、数据依赖、条件和调用组织实现该行为？ |
| CoT 表达     | 如何向 victim 说明这份实现与当前任务的关系？         |
| trigger      | 示例与查询采用什么固定的 trigger 条件？               |

面向 SAST 的结构研究关注**目标模式仍然成立、指定 SAST 未检出的结构**。结构是可以修改的对象，是否检出是需要测量的结果，两者分别描述。

### 4.2 代码侧留下哪些自由

执行模型可以改变实现目标模式的那部分代码操作（下称“目标操作”）在程序中的具体表示和组织，而不只调整变量名称或注释。下面列出结构层面的开放选择。


| 结构方面 | 允许探索的内容                               | 需要理解的问题                                   |
| ---------- | ---------------------------------------------- | -------------------------------------------------- |
| 具体表示 | 表达同一目标模式的表达式、取值方式与调用形式 | 表面表达变化后，目标模式与任务行为是否仍成立？   |
| 数据依赖 | 输入、配置、中间结果与目标操作之间的关系     | 这些关系怎样影响功能、oracle 判定和示例的可理解性？ |
| 控制流程 | 目标操作与任务分支、执行条件及异常处理的关系 | 目标操作在什么条件下发生，是否保留完整任务逻辑？ |
| 程序组织 | 目标逻辑与任务主逻辑的划分、复用和组合       | 哪种组织既适合当前任务，也便于在其他任务中采用？ |

这些选择可单独调整或组合变化。起点只提供一份未体现目标模式的 clean 实现，执行模型可以在候选中探索新的结构，并同步调整 CoT。

### 4.3 要解决的是结构在 victim 生成过程中的保留与变化

一个示例中的结构可能符合目标模式与检测要求，victim 却采用不同的实现，也可能保留目标模式但改变其结构，或采用结构后遗漏任务功能。因此需要分别观察：

- **示例中怎样实现**：目标模式、结构、功能与 SAST 结果。
- **输出中怎样实现**：victim 是否采用目标模式，结构被保留、改写还是替换，以及对应功能与 SAST 结果。

这里的关键问题是：**什么结构既能体现目标模式，又能在 victim 生成的不同任务代码中形成可用实现，并呈现怎样的检测结果？** CoT 的探索围绕这个代码对象展开，两者共同构成候选。

## 5. 修改空间：后三个示例的 code/CoT 自由改写

六条经验给出关注方向，本节确定执行模型的自主选择范围。一个候选包含完整的四个示例，其中后三个示例的 code/CoT 可以局部修改、组合修改或整体重写。


| 对象               | 执行模型可自由决定                                             | 保持的内容                                          |
| -------------------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| 后三个示例的 code  | 结构的具体表示、数据依赖、控制流程、程序组织与修改幅度 | 任务要求的接口与功能；按已声明目标检查              |
| 后三个示例的 CoT   | 措辞、详略、步骤、解释与代码提示的组合                     | 解释当前示例，说明与实现相符                        |
| code 与 CoT 的关系 | 只改一侧或共同重写，重新安排对应关系                       | 各示例的任务含义                                    |
| 多个示例的关系     | 修改部分或全部，决定共性与任务差异                         | 示例 1、任务内容、示例数量与顺序                    |
| CoT 内的 trigger   | 是否出现、位置及语句衔接                                   | trigger 内容固定，每个可修改 CoT 至多一次；题面渲染规则固定 |

**原句、行内代码提示、步骤位置和具体代码形式均可调整；是否使用额外标签也留给探索。** 执行模型可以提出表外的组织方式。固定任务演示只作构造参照，不自动套用到初始模板。研究范围排除要求后续查询模仿目标模式的元指令，包括带此类末尾指令的 B8 等历史模板。

## 6. 预计解决的问题：代码实现结构、表达稳健性与任务适应

后续方法围绕下面六个问题设计。重点是探索代码实现结构与 CoT 表达如何共同适应任务，并理解结构变化、模式采用、检测结果和功能之间的关系。


| 开放问题                         | 需要探索什么                                                                                           |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **什么结构值得采用？**       | 在目标模式与任务功能成立的前提下，理解不同结构的 SAST 检出差异，以及结构在 victim 输出中的保留与变化。 |
| **哪些信息真正需要保留？**       | 区分需要准确表达的含义与可以替换的词句、代码提示和位置，减少对偶然措辞的依赖。                         |
| **如何兼顾共性与任务差异？**     | 让共同实现思路适应不同任务，找出有意义的任务相关调整。                                                 |
| **如何区分功能退化与任务难度？** | 结合 clean 参照识别失败原因，探索功能与目标模式同时成立的表达。                                        |
| **解释形式怎样适应不同代码？**   | 判断哪些解释原则可迁移，哪些需要随具体实现或 CWE 调整。                                                |
| **什么经验值得继续相信？**       | 区分可重复的线索、局部现象和待验证判断，使初始经验得到持续修正。                                       |

**论文的问题定位：在原始 clean few-shot 完整模板和少量直观经验的基础上，探索目标模式的代码实现结构及其 CoT 表达，理解它们在不同任务中的采用、功能保持（以功能通过衡量）和 SAST 检出表现。** 注意力与上下文学习提供理解这些问题的角度。具体角色、算法、候选选择和预算安排留待方法设计。

### A.3 集中保留的解释边界

- **计数与来源**：三题重复采样不是多道独立任务；26 题筛选含已用于开发的题。最终任务按协议划分并披露开发期使用情况，不能将筛选结果直接写成未见任务泛化效果。
- **测量版本**：功能修正改变对已有输出的评价，不代表模板效果取得新提升，也不表示全部历史响应都按同一新版测试重跑。
- **起点选择**：2026-10-26 曾按用户选择把 B2-nolabel 设为默认起点；2026-10-27 用户改为原始 clean few-shot，B2-nolabel 改作固定任务演示。B2-nolabel 的三题 ×10 与历史 B2-r20 并非同批对照，repeat 与功能测试口径也有差异。这些结果支持将其用作演示来源，不证明去掉 `key:` 带来性能提升；B2 的 26 题结果仍只属于 B2。
- **跨批比较**：旧稿曾将 v1 的B2三题40/60与单独修复t16后的结果拼接为约53/60。这是跨条件重建，不作为新的三题实测或通用波动阈值；实际重采按各批原始记录比较。
- **结构与检测**：B2/B2-nolabel/A2/A4 的对照主要改变 CoT，不能据此排列代码实现结构的优劣。“未检出”绑定具体工具和规则；扫描失败或 oracle 无法确认目标时，分别保留未知状态。
- **因果解释**：多项一起变化时，先解释整份候选的表现。注意力、上下文学习及 code/CoT 协同目前属于解释假设；没有检出差异也不等于无效。
- **模板完整性**：B2、B2-nolabel、A2、A4 都省略了示例810的部分分支说明，而代码保留分支。当前起点是原始 clean-fewshot，其 CoT 按原样保存；若参照演示采用 B2-nolabel 构造，应自行补回该分支解释。正式采用前按协议的示例门检查；修订后保存新版本，旧分数对应原模板。
